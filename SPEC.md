## 0. Original vision

> **PROVISIONAL — reconstructed by Claude from the project name, README, and design docs; not yet confirmed by the author.** This is the one section code-reading cannot recover, so it is written from the strongest available intent signals and takes explicit positions on the questions in §7 that the Phase-3 architecture depends on. **Author: correct anything wrong here before Phase 4 (implementation); the checklist at the end of this section flags the load-bearing calls I made on your behalf.**

**Mission.** SwartzNet exists to make the material people already share *findable by what it contains*, without asking anyone to adopt a new network, run new infrastructure, or trust a central index. Plain BitTorrent can only find content you already know the infohash of; SwartzNet lets you search inside the files you've downloaded and discover torrents by topic — riding the exact same mainline DHT and peer wire that every existing client already speaks. The name reads as a tribute to Aaron Swartz and an alignment with open access to information: knowledge should be discoverable and preservable by the people holding it, not gated behind silos or takedown-prone central search. *(Inference — confirm or replace with your own framing.)*

**Who it's for.** The design center is people who build and share durable collections — archivists, researchers, librarians, and technically-comfortable seeders — for whom "I have the files but no one can find them" is the real problem. "Anyone with a magnet link" is the floor the client must still serve, not the design target.

**The three-layer bet.** The whole architecture is one wager: you can add real search to BitTorrent *without breaking mainline compatibility* by stratifying it. Layer L (local full-text index) is private and always works. Layer S (`sn_search`, a hidden LTEP extension) shares search with peers you're already connected to, invisible to vanilla clients. Layer D (BEP-44 mutable items on the mainline DHT) makes keyword→infohash pointers globally discoverable using only standard DHT storage. Each layer degrades independently; none requires anyone else to upgrade.

**Trust is local and social, never global.** No token, no blockchain, no consensus, no global ranking authority. Discovery is defended with local, individually-owned mechanisms: a persistent ed25519 identity, publisher-signed torrents, user-curated allowlists, per-publisher Bayesian reputation, and a known-good Bloom filter. A node's view of "who to trust" is its own. *(This is a deliberate rejection of Tribler's flood-query model and of any global-ledger approach — see docs 02/03/10.)*

**Invariants — what must never change** (evidenced by CLAUDE.md and the code, not just inferred):
- **Mainline wire compatibility is absolute.** No new reserved bit, no new DHT verb, no new UDP port. A vanilla peer must observe only BEP-3/5/9/10/44/46/51 traffic. Any change that would break this is a defect, full stop.
- **Identity is persistent and load-bearing.** `identity.key` (mode 0600) backs publisher reputation and signing; losing it loses standing. Never regenerate implicitly.
- **The control plane is localhost-only and unauthenticated by construction.** The HTTP API's security model *is* the loopback bind. It must never become network-reachable without an explicit, separate auth design.
- **One daemon, three coequal frontends.** CLI (with embedded web UI), native GUI, and any future frontend obtain a fully-wired node from a single constructor. Subsystem lifecycle lives in exactly one place.

**The distributed-layer endgame ("Aggregate").** The v0.5 "Aggregate" redesign (per-publisher PPMI pointers + a signed, PoW-gated B-tree index format + RIBLT set reconciliation) is the *intended future* of Layer D — an approved design with a byte-level spec, not a discarded experiment. **Provisional position for the rebuild:** treat the legacy per-keyword BEP-44 path as the shipping baseline that must keep working, and the Aggregate format as a cleanly-separated migration target that is *not yet load-bearing*. The rebuild should make the Layer-D record format and publish/lookup path a swappable seam so the migration questions in §7-C can be answered without re-architecting. *(This is a significant call — see checklist.)*

**Explicitly out of scope** (provisional — these bound the rebuild):
- **Anonymity.** SwartzNet is not Tor/I2P. It rides the clear mainline DHT and reveals the same metadata any BitTorrent client does. Privacy knobs (`--no-dht-publish`, per-torrent indexing opt-out) reduce *what you publish*, not *who can see you*.
- **NAT traversal** beyond what `anacrolix/torrent` already provides.
- **Mobile / embedded** frontends.
- **Any global consensus, ledger, token, or currency.**

## 1. Core purpose

SwartzNet is a mainline-compatible BitTorrent client with built-in distributed full-text search. It downloads and seeds ordinary torrents like any client, but additionally extracts text from completed files into a local search index (Layer L), lets peers query each other's indexes over an ordinary BitTorrent connection via a hidden LTEP extension (Layer S, `sn_search`), and publishes/looks up signed keyword→infohash mappings on the mainline DHT as BEP-44 mutable items (Layer D). The load-bearing constraint across all of it: a vanilla BitTorrent client interacting with a SwartzNet node must observe only standard BEP-3/5/9/10/44/46/51 traffic — no new reserved bit, no new DHT verb, no new UDP port.

Everything is one Go binary per frontend (CLI with embedded web UI, native Fyne GUI) wired through a single daemon constructor; a persistent ed25519 identity underpins torrent signing, publisher reputation, and spam resistance for search results. Trust is local and social: allowlists, Bayesian per-publisher reputation, a known-good Bloom filter — no global consensus, no token.

## 2. Capabilities (user-facing behavior)

### 2.1 Running a node (daemon lifecycle, CLI `add`, config & paths)

**CLI binary and dispatch.**
- `swartznet <cmd>` dispatches to the subcommands `add`, `search`, `status`, `flag`, `confirm`, `create`, `index`, `files`, `trust`, `aggregate`, `crawl-probe`, `version` (also `-v`/`--version`), and `help` (also `-h`/`--help`). Zero arguments or an unknown command prints usage to stderr and exits 2 (cmd/swartznet/main.go:43-85).
- Exit-code contract (relied on by shell scripts): 0 = OK, 1 = runtime error, 2 = usage error, 130 = clean interrupt — SIGINT/SIGTERM cancel the run context and `context.Canceled` maps to 130 (cmd/swartznet/main.go:30-35,184-195).
- Log level for daemon-running commands comes from env `SWARTZNET_LOG` (`debug|info|warn|error`, default `info`); structured slog text goes to stderr (cmd/swartznet/main.go:138-151; cmd/swartznet/cmd_add.go:92).

**`add` — the daemon command.**
- `swartznet add <magnet-uri | path.torrent>` IS the node: it constructs the full daemon (engine + indexer + companion publisher/subscriber + HTTP API), adds the one torrent, and runs until Ctrl-C. An argument with the `magnet:` prefix is added as a magnet; anything else is treated as a `.torrent` file path (cmd/swartznet/cmd_add.go:96-146,149-160).
- After adding, the node waits up to 5 minutes for metadata (timeout is a runtime error, exit 1), prints name/infohash/total size/piece count/first 20 files, starts downloading all files, then prints a one-line progress status every 3 seconds plus one line per newly completed file, until interrupted (exit 130) (cmd/swartznet/cmd_add.go:124-146,160-181,187-231).
- Flags: `--data-dir`, `--index-dir`, `--port` (default `-1` sentinel = keep config default 42069; `0` = OS-assigned), `--api-addr` (default `localhost:7654`; empty string disables the HTTP API), `--no-dht` (disable mainline DHT entirely), `--no-dht-publish` (privacy mode: stay on the DHT but publish no BEP-44 items), `--leech-only` (disable upload), `--no-index`, `--dht-bootstrap host:port` (repeatable; empty = library defaults), `--regtest`, `--dht-insecure` (cmd/swartznet/cmd_add.go:38-49,82-90).
- Fail-closed safety guard: `--regtest` and `--dht-insecure` are refused with exit 2 and an explanatory message unless env `SWARTZNET_UNSAFE=1`, so copy-pasted testbed commands cannot weaken a mainnet node (cmd/swartznet/cmd_add.go:59-73).
- On successful startup the command prints which optional subsystems came up: companion publisher (with its dir), companion subscriber, and the HTTP API listen address (cmd/swartznet/cmd_add.go:109-117).

**Daemon construction (one wiring point for all frontends).**
- `daemon.New(ctx, Options)` returns a fully wired node used identically by the CLI, the native GUI, and (via the embedded web UI) the HTTP API; frontends differ only in presentation. Startup order is fixed: engine → indexer → companion publisher → companion subscriber → aggregate bootstrap → session restore → HTTP API (internal/daemon/daemon.go:86-258; cmd/swartznet-gui/main.go:103).
- Degraded startup instead of abort: only engine construction and indexer open failures make `daemon.New` return an error (an indexer failure also closes the already-started engine). Companion publisher/subscriber, aggregate bootstrap, and HTTP API start failures print a `warning:` line to `Options.Stderr` (io.Discard when nil) and the node runs without that subsystem (internal/daemon/daemon.go:79-84,112-130,141-146,155-161,197-199,250-254).
- `Options.NoIndex` (CLI `--no-index`) is a global opt-out: it skips opening Bleve entirely (no index handle) AND mirrors into the config so the engine also suppresses the Layer-D BEP-44 keyword publisher (internal/daemon/daemon.go:96-98,121-130).
- The companion publisher starts only when ALL of: index open, engine DHT put path available, engine identity present, and `CompanionDir` non-empty; it writes artifacts into `CompanionDir`, never `DataDir`. Regtest swaps in accelerated publisher timings (internal/daemon/daemon.go:132-147).
- The companion subscriber starts when index + DHT get path + `CompanionDir` are present (no identity needed). At startup it loads the follow list from `CompanionFollowFile`: a missing file yields an empty list; a corrupt or oversized file is warn-logged (`daemon.companion.load_follow_file_err`) and treated as empty — follows remain addable via the API (internal/daemon/daemon.go:149-178; internal/daemon/follows.go:48-91).
- Follow/unfollow requests via the HTTP API mutate the in-memory subscriber AND atomically rewrite `companion-follows.json` (tmp+rename, mode 0600) under a mutex so the list survives restart; persistence is silently skipped when the follow path is empty (internal/daemon/adapters.go:198-246).
- Aggregate cold-start bootstrap is constructed only when the engine has a DHT lookup (DHT on). Channel A fetches each configured anchor pubkey's PPMI in parallel and admits successes into the lookup set, marking them reputation-seeded; a background loop re-runs channel A whenever the HTTPS fallback later adds anchors (initial run only if anchors were already configured) (internal/daemon/daemon.go:180-221; internal/daemon/bootstrap.go:178-246).
- Channel C admission: swarmsearch peer-announce endorsements feed the bootstrap; a candidate publisher is admitted when already admitted, or when ≥ 3 distinct endorsers each hold tracker reputation ≥ 0.5, or when the bloom policy passes. Publisher pubkeys observed in sync records feed the crawl channel with signature-valid status (internal/daemon/daemon.go:48-65,204-208; internal/daemon/bootstrap.go:259-319).
- Admission state (admitted/pending/anchor counts) is surfaced to operators through the `/aggregate` HTTP endpoint; admissions refused due to the cap are logged `daemon.aggregate_bootstrap.admit_capped` so a starved node is distinguishable from a quiet network (internal/daemon/bootstrap.go:321-388,407-412; internal/httpapi/server.go:214-218).
- HTTPS last-ditch anchor fallback: fetches a JSON anchor list over HTTPS only (loopback plain-HTTP allowed solely via a test-only client flag), caps the response body at 64 KiB, silently skips malformed hex entries, dedupes, appends new anchors, and wakes the anchor loop via a buffered coalescing channel (internal/daemon/bootstrap_https.go:38-63,106-124,149-219).
- When `Options.APIAddr` is non-empty the HTTP API starts with the daemon's version in `/healthz` and adapters exposing: index search, swarm search, Layer-D publisher/lookup, bloom, reputation tracker, source tracker, torrent add, full torrent control (add-magnet, pause, resume, remove, per-torrent indexing toggle, file list, per-file priority, up/down rate limits, max active downloads, snapshots), companion status/refresh/follow, DHT routing-table stats, and the bootstrap probe (internal/daemon/daemon.go:230-255; internal/daemon/adapters.go:23-120).
- Session restore runs during startup: every torrent in the on-disk session manifest is re-added so users see their previous list; per-entry failures are warn-logged and the aggregate error is deliberately ignored so restore can never block startup (internal/daemon/daemon.go:223-228).

**Daemon shutdown.**
- `Daemon.Close` tears down in exact reverse order: cancel the daemon-owned background context and join background goroutines FIRST (so no anchor fetch touches the engine mid-teardown), then stop the HTTP API with a 3-second timeout, companion subscriber, companion publisher, index, engine (internal/daemon/daemon.go:260-287).

**Configuration and paths.**
- `Config.Default()` yields a usable out-of-the-box node: `ListenPort` 42069, `Seed=true`, and all persistent state rooted at the XDG share root — preference order `$XDG_DATA_HOME/swartznet`, then `$HOME/.local/share/swartznet`, then `./swartznet-data` as last resort. Paths: `data/` (content), `index/` (Bleve), `identity.key`, `publisher.json`, `reputation.json`, `seeds.json`, `known-good.bloom`, `companion/`, `companion-follows.json`, `trust.json`; `MinIndexerScore` 0 (internal/config/config.go:231-250,302-314).
- `Config.Validate()` (invoked by engine construction) rejects an empty `DataDir` and ports outside 0–65535, creates `DataDir` (0755) and `IndexDir`'s PARENT (Bleve creates the leaf itself), and fail-closed rejects `Regtest`/`DHTInsecure` unless running inside a `go test` binary or `SWARTZNET_ALLOW_REGTEST=1` is set (internal/config/config.go:255-300; internal/engine/engine.go:550).
- GUI settings persistence writes only `{data_dir, index_dir}` to `<shareRoot>/config.json` (pretty JSON, tmp+rename, 0644; empty fields omitted so defaults reapply). Loading treats a missing file as a no-op but errors on malformed JSON. Precedence: defaults ← saved overrides ← CLI flags (internal/config/config.go:365-438; cmd/swartznet-gui/main.go:67-96).

**Thin-client and offline subcommands** (drive a running daemon over the localhost HTTP API, or operate on local files with no daemon):
- `search <query...>` (words joined with spaces): local mode opens the Bleve index in-process (no daemon needed) and prints text or `--json` results, distinguishing `[content]` hits (path, mime, extractor, parent infohash) from `[torrent]` hits (name, infohash, file count, size, first tracker + tracker count) (cmd/swartznet/cmd_search.go:55-91,235-264).
- `search --swarm` / `--dht` / `--signed-by <64-hex-pubkey>` switches to `POST /search` on the running daemon, combining local + sn_search peer fan-out + BEP-44 DHT lookup in one call; text output renders separate LOCAL/SWARM/DHT sections with per-layer asked/responded/rejected/hit counts and per-layer error strings. Flags: `--limit` (default 20), `--swarm-timeout-ms` (2000), `--dht-timeout-ms` (5000), `--api-addr` (cmd/swartznet/cmd_search.go:43-51,95-146,150-196).
- `status` GETs `/status` and prints Layer L doc count, Layer S known/capable peers, DHT routing-table nodes (block omitted when the daemon runs with DHT disabled), and Layer D publisher pubkey plus per-keyword hits/publish-count/last-published/error state; it also best-effort GETs `/aggregate` and appends a PPMI/B-tree/RIBLT block. `--json` merges both into one document `{status, aggregate}` (cmd/swartznet/cmd_status.go:34-105,107-193).
- `flag <infohash>` POSTs `/flag` to demote the reputation of every indexer attributed to that infohash; `confirm <infohash>` POSTs `/confirm` to add it to the known-good Bloom filter (the manual counterpart to the engine's auto-confirm-on-completion). Both lowercase/trim and validate the 40-hex infohash locally before any network call and print `flagged:`/`confirmed:` on success (cmd/swartznet/cmd_flag.go:17-35,45-53,83-95).
- `trust list|ls`, `trust add <pubkey> [label...]`, `trust remove|rm <pubkey>` manage a local offline JSON trust list (default `~/.local/share/swartznet/trust.json`; `--file` overrides; `--json` for list). Works with no daemon running; `add` lowercases/trims the pubkey and joins remaining args into the label (cmd/swartznet/cmd_trust.go:14-52,91-157).
- `aggregate build --out FILE [--in JSONL|-] [--key path] [--seq N] [--piece-size N] [--pow-bits N]` reads JSONL `{kw,ih,t}` records, signs each with the publisher ed25519 key, optionally mines hashcash PoW per record, packs them into a signed B-tree index file (mode 0644), and prints records/pages/bytes/fingerprint. Fully offline — never touches DHT or daemon (cmd/swartznet/cmd_aggregate_build.go:38-108,196-236).
- `aggregate inspect <index-file> [--piece-size]` opens the B-tree (failing on bad magic/version/trailer signature) and prints trailer metadata: pages, records, publisher pubkey, seq, created timestamp, min PoW bits, tree fingerprint. `aggregate find <index-file> <prefix> [--piece-size] [--verify]` runs a keyword prefix query and prints matching (infohash, keyword, timestamp) records; `--verify` additionally validates the tree fingerprint by scanning every leaf (cmd/swartznet/cmd_aggregate.go:66-160).
- `crawl-probe --addr host:port [--target 40hex] [--timeout-ms 5000] [--json]` issues a single BEP-51 `sample_infohashes` query from a throwaway loopback DHT server (BEP-42 security off, passive) and prints interval, num-tracked, sampled infohashes, and closest nodes; the target defaults to a fresh random 20-byte ID per run (cmd/swartznet/cmd_crawl_probe.go:30-142).
- `cmd/dht-smoke` is a separate ops probe binary (excluded from `go test`): it bootstraps a real mainline DHT server (waits up to 30 s for ≥ 8 good nodes, fails if < 1), generates an ephemeral ed25519 key, Puts a synthetic keyword value under a timestamped salt, Gets it back, and verifies hits==1 and name=="smoke test" — printing PASS (exit 0) or FAIL (exit 1). `-stress N [-stress-timeout 60s] [-stress-concurrent 8]` additionally runs N concurrent BEP-44 puts, reporting success rate, min/p50/p95/max latency, error buckets, post-load routing stats, and one sample get-back round trip (cmd/dht-smoke/main.go:53-328).

### 2.2 Downloading, seeding, and torrent management (engine)

**Adding torrents (four paths).**
- By magnet URI: the URI is parsed locally first so invalid or zero-infohash magnets fail fast with an error instead of crashing the daemon; the add is recorded in the session manifest and metadata fetch continues asynchronously. The HTTP-API variant wraps the whole call in a panic recover so pathological input becomes a 400, never a crash (internal/engine/engine.go:1141-1186).
- By `.torrent` file: an optional SwartzNet ed25519 signature (`snet.pubkey`/`snet.sig` fields) is verified at add time; a verified pubkey becomes the handle's `SignedBy` (surfaced in snapshots and the session), while a bad signature is logged as rejected but the torrent still adds. The original raw bytes are copied to `<DataDir>/torrents/<infohash>.torrent` so restore works even if the user deletes the source file (internal/engine/engine.go:1189-1244).
- By raw 20-byte infohash (used by the companion subscriber for BEP-46 pointer targets): a zero infohash is rejected up front and the client call is wrapped in recover because the infohash is attacker-controlled (internal/engine/engine.go:1262-1283).
- By in-memory metainfo, immediately seeding (create-torrent and companion-publisher flows): optionally with per-torrent storage rooted at the content's real on-disk location so a torrent created outside `DataDir` seeds in place instead of showing 0%. A background full-data rehash is kicked so progress reflects on-disk state without waiting for peers; metainfo plus DataPath/ContentName persist to the session (internal/engine/engine.go:1391-1538).

**Metadata arrival and auto-download.**
- When metadata arrives, every file is flipped to Normal priority per-file (deliberately not a whole-torrent download-all) so both priority surfaces update and the Files UI shows "normal"; the flip respects paused state and the download-slot cap, and the engine gives up after 5 minutes if metadata never arrives (internal/engine/engine.go:1919-1939).
- Magnet-to-file session upgrade: once metadata arrives for a magnet/infohash-added torrent, the metainfo is serialized into `torrents/` and the session entry gains a TorrentFile so future restarts skip the ut_metadata round trip; `AddedVia` stays `magnet`/`infohash` for posterity (internal/engine/engine.go:1669-1715).

**Session persistence and restore.**
- Every add/pause/resume/indexing-toggle/queue change atomically rewrites `<DataDir>/session.json`. Restore (invoked by the daemon at startup) re-adds every entry in queue order, preferring the on-disk `.torrent` copy, then magnet URI, then bare infohash, re-applying paused/indexing/queue-order/signedBy and seed-from storage. Per-entry failures are logged and skipped, never fatal; every restored torrent gets a background data rehash so partial downloads resume at their real percentage (internal/engine/engine.go:1726-1899; internal/engine/session.go:13-235).

**Download queue.**
- A max-active-downloads cap (0 = unlimited) bounds concurrent downloads; over-cap torrents sit "queued" — metadata fetch and indexing still run, only the file-priority flip is deferred. Promotion is FIFO by a monotonic per-handle queue order, re-evaluated on pause, remove, completion, or cap raise; move-to-front/back reassign order to min−1/max+1. A promotion mutex serializes count-then-activate so batch restores cannot over-subscribe the cap (internal/engine/queue.go:5-265; internal/engine/engine.go:123-131).

**Pause/resume and removal.**
- Pause is a soft stop — data download and upload are disallowed but peer connections stay open for sn_search — and frees a download slot; resume re-runs queue-or-activate so a torrent paused before metadata still gets its priorities flipped later. Both are idempotent and persisted (internal/engine/engine.go:2355-2403).
- Remove closes the torrent's subscriptions and removed-channel (releasing per-handle goroutines), drops the underlying torrent, deletes the session entry and its `.torrent` copy, retracts the infohash's DHT keywords from the publisher manifest, and promotes the next queued torrent — but leaves downloaded data on disk and Bleve entries in the index (internal/engine/engine.go:2437-2472; internal/engine/session.go:167-180).

**Per-file control.**
- The per-file view returns index/path/length/completed-bytes/progress/priority per file (empty slice before metadata); per-file priority accepts `none|normal|high`, where `none` removes the file from the download set (internal/engine/files.go:75-136).
- CLI: `files <infohash>` GETs `/torrents/{ih}/files` and prints an IDX/PRIORITY/SIZE/PROG%/PATH table (or `--json`); `files <infohash> <idx> <priority>` POSTs `/torrents/{ih}/files/{idx}/priority`, with priority restricted to `none|normal|high` and idx validated and canonicalized as a non-negative integer before URL interpolation (cmd/swartznet/cmd_files.go:22-151).

**Rate limits.**
- Upload/download rate limits are runtime-mutable and shared by all connections; 0 or negative means unlimited, and getters report 0 for unlimited (internal/engine/ratelimit.go:20-56).

**Completion events.**
- Per-torrent event streams: raw piece-state changes (buffer 64, drop-on-full with a debug log) and file-completion events — exactly one event per file the first time all its pieces verify, fanned out to any number of subscribers with a replay buffer covering files already complete at subscribe time (internal/engine/piece_sub.go:35-107; internal/engine/file_tracker.go:14-233).

**Hooks into the search layers.**
- Auto-indexing (Layer L): with an index attached, each torrent's metadata-level document (infohash, name, file paths, trackers, size, file count, signedBy) is written to Bleve on metadata arrival, and each completed file is submitted to the content-extraction pipeline (100 MiB per-file extraction cap) via a lazy reader. Per-torrent opt-out (`SetTorrentIndexing`) is prospective-only and persisted; detaching the index unwires both the pipeline and the sn_search local searcher. CLI: `index <infohash> on|off` (also accepts `true/1/yes` and `false/0/no`) POSTs `/torrents/{ih}/indexing` on a running daemon (internal/engine/engine.go:306-331,1995-2115; cmd/swartznet/cmd_index.go:18-77).
- Layer-D publishing: on metadata arrival the torrent's keywords go to the DHT BEP-44 publisher (unless suppressed by no-index or no-dht-publish), and one signed local record per tokenized keyword of the name is minted into the record cache (PoW=0 during the current migration window) for sync-session responders; removal retracts the infohash from the publisher manifest (internal/engine/engine.go:248-283,2084-2097,2459-2466).
- sn_search (Layer S) wiring: the extension is advertised in every outbound LTEP handshake, remote capability is recorded from the extended handshake, inbound frames are dispatched asynchronously off the read loop with a 256-slot admission semaphore (overflow frames dropped) and a separately gated reply writer (overflow replies fail with a reply-overloaded error); addr→conn tracking supports outbound query fan-out, and peer state is dropped on connection close (internal/engine/engine.go:692-802,838-851; internal/engine/swarmadapter.go:25-57).
- DHT wire-compat setup: an in-memory peer store makes get_peers replies carry BEP-5 write tokens; caller-provided bootstrap node lists are honored; BEP-42 node-ID security can be opted out for private/docker DHTs; BEP-44 item expiry is pinned to 2 h when the library leaves it 0 (which would instantly expire every stored mutable item) (internal/engine/engine.go:574-636).

**Reputation, identity, and trust lifecycle.**
- At startup the engine loads the known-good Bloom filter, the reputation tracker (plus a curated seed list of ~20 maintainer pubkeys carrying a decaying +0.45 bonus), the trust store, and an always-present in-memory source tracker, wiring them into DHT lookup with an optional minimum indexer score. On download completion the infohash is auto-added to the Bloom filter; a torrent signed by a trusted publisher is Bloom-confirmed immediately at add time. Bloom + reputation persist on shutdown (internal/engine/engine.go:886-944,1949-1986,2099-2114,2518-2527).
- Publisher identity: the persistent ed25519 identity is loaded or created, a shared BEP-46 pointer putter/getter is built (the putter exists even in leech-only mode for the user's own companion publications), the node adds itself as a known indexer so `--dht` self-search works, gossip-discovered pubkeys feed the lookup, and the Publisher capability bit is set only when actively publishing so passive nodes don't gossip themselves as indexers (internal/engine/engine.go:966-1100).

**Companion-index fetch (engine side).**
- Fetching a companion index by infohash waits for metadata, rejects multi-file torrents, rejects declared size > 32 MiB before requesting any piece, rejects unsafe names (path separators, dot entries, backslash), downloads fully with a 250 ms completion poll, and returns `DataDir/<name>`; context cancellation aborts the wait but leaves the torrent for retry reuse (internal/engine/engine.go:1290-1376).

**Snapshots for GUI/API.**
- Per-torrent snapshots report progress, peer counts, seeders, a status string (`metadata/downloading/seeding/paused/queued`), per-second transfer rates sampled against the previous call (zeros on first call; cached result if < 100 ms since the last sample), indexing-progress counters, SignedBy, and a trusted-publisher badge — all defensively computed pre-metadata to avoid nil-info panics (internal/engine/engine.go:2156-2345).

**Shutdown and operational modes.**
- Engine close is ordered and idempotent: cancel background context → stop extraction pipeline → stop DHT publisher → save bloom + reputation → close all piece/file subscriptions → close the torrent client; repeated close returns the cached error (internal/engine/engine.go:2494-2538).
- Regtest mode logs a loud "DO NOT USE IN PRODUCTION" warning and accelerates the feeler interval, record-cache pruning (every 200 ms, 500 ms max age), and publisher timings so scenario tests observe hourly/daily cycles in seconds (internal/engine/engine.go:815-825,847-862,1032-1035).
- Record-cache hygiene: FIFO cap of 100,000 records and an hourly prune dropping records older than 30 days (internal/engine/engine.go:56-70,857-880).
- Test/ops accessors expose local port, DHT address, DHT routing-table size (good/total), handle lookup by infohash, and an explicitly-not-for-production helper that cross-wires two in-process engines as peers for test clusters (internal/engine/engine.go:2540-2619).

### 2.3 Creating and signing torrents

**CLI `create`.**
- `swartznet create <file-or-folder> -o <out.torrent>` hashes the content in-process using a minimal engine (deliberately not the full daemon), writes the `.torrent`, and prints the infohash. Flags: `-o` (required output path), `--name` (override info.name; default = basename of root), `--piece-kib` (piece length in KiB, 0 = auto), `--tracker` (repeatable), `--webseed` (repeatable), `--comment`, `--private` (BEP-27, disables DHT/PEX), `--sign`, `--identity`, `--seed`, `--data-dir` (with `--seed`, directory for session state; content is seeded in place from `<root>`). The CLI sets CreatedBy to `swartznet <Version>` (cmd/swartznet/cmd_create.go:25-137,41-51,81).
- `--sign` signs the `.torrent` with the ed25519 identity and prints `Signing with identity <pubkey>`. The default identity path is auto-created if missing (load-or-create), but an explicitly passed `--identity` path is load-only and errors if the file is absent. `--identity` without `--sign` is a usage error (fail closed) (cmd/swartznet/cmd_create.go:64-70,87-104).
- `--seed` then seeds the just-created content in place from `<root>` (path-aware add keyed on the root's real basename), blocking until Ctrl-C (exit 130). A seed-start failure prints a warning and exits 1 even though the `.torrent` was already written (cmd/swartznet/cmd_create.go:138-157).

**Engine torrent creation.**
- Creating from a local file or directory supports: automatic piece length selection when unset, name override, a tracker list where the first URL becomes `announce` and all URLs form one announce-list tier, BEP-19 web seeds, the BEP-27 private flag, a comment, and CreatedBy defaulting to `"SwartzNet"` when the caller passes none. The output file is written atomically (tmp+rename) and the call returns the hex infohash (internal/engine/create.go:79-195,147-150).

**Signing model.**
- Signing is infohash-preserving: the ed25519 signature and pubkey live in top-level `snet.pubkey`/`snet.sig` fields outside the info dictionary, so signed and unsigned copies of a torrent share the same infohash and remain fully consumable by vanilla clients (internal/engine/create.go:79-195; internal/engine/engine.go:1189-1244).
- Verification happens at add time on the consuming node: a valid signature attaches the publisher pubkey to the torrent handle (`SignedBy`, surfaced in snapshots, session, and search); an invalid signature is logged as rejected but never blocks the add. A signature from a publisher on the local trust list additionally Bloom-confirms the infohash immediately (see 2.2) (internal/engine/engine.go:1189-1244,2099-2114).
- The signing identity is the node's persistent ed25519 keypair at `~/.local/share/swartznet/identity.key` (mode 0600), shared with Layer-D publishing; losing it means losing publisher reputation, and it is never regenerated implicitly for an explicitly named path (cmd/swartznet/cmd_create.go:87-104; internal/engine/engine.go:966-1100).

### 2.4 Search Layer L — local full-text index

Layer L is a Bleve full-text index over two document types: torrent-level metadata docs and content-level docs holding text extracted from completed files. It is the only layer that touches disk-resident search state; Layers S and D never see Bleve internals.

**Query behavior**

- A search accepts Bleve QueryString syntax — terms OR'd by default, `+required`, `-excluded`, `"exact phrase"`, `field:term`, `fuzzy~1`, `boost^2` — and returns interleaved torrent-level and content-level hits sorted by relevance score. Each hit carries the infohash plus, for torrent hits, name/size/trackers/signed_by, and for content hits, file path/index/mime/extractor; hits may include `<mark>`-wrapped highlight fragments; the response carries a total count and query duration (internal/indexer/indexer.go:668-818, 629-666).
- A request may filter to torrents signed by a specific 64-char hex ed25519 pubkey (`SignedBy` facet), combinable with a text query or standing alone — an empty query plus SignedBy is valid and returns all of that publisher's signed torrents (internal/indexer/indexer.go:617-621, 696-730).
- Four consumers reach the same Search entry point: CLI `swartznet search` opens the Bleve dir directly (no daemon) unless `--swarm`/`--dht`/`--signed-by` routes it via POST /search; HTTP POST /search produces the Local section of the combined response; the GUI Search tab calls it directly; and Layer-S peer queries are answered from this index through an adapter (cmd/swartznet/cmd_search.go:19-91; internal/httpapi/server.go:524-553; internal/gui/search.go:168-172; internal/engine/swarmadapter.go:66-92).

**Document schema and IDs**

- TorrentDoc fields: 40-char lowercase hex infohash, name, all file paths (joined with `\n` for analysis), tracker URLs, total size bytes, file count, AddedAt timestamp (defaults to now-UTC if zero), and SignedBy (64-hex ed25519 pubkey, lowercased, empty for unsigned). Doc ID is `t:<lowercase-infohash>`, so re-indexing the same torrent is a pure replace (internal/indexer/indexer.go:171-213).
- ContentDoc fields: infohash, file index, file path, file size, MIME type, extracted text, extractor name, IndexedAt, and chunk index (0 for whole-file). Doc ID is `c:<lowercase-infohash>:<fileIndex>:<chunkIndex>`, so re-extraction overwrites rather than duplicates (internal/indexer/content.go:22-41).

**Automatic ingestion**

- When a torrent's metadata arrives (the node waits up to 5 minutes for GotInfo), a TorrentDoc is written to the index — unless the per-torrent indexing toggle is off (internal/engine/engine.go:2035-2081; internal/indexer/indexer.go:218-228).
- Every file-complete event on an indexing-enabled torrent is submitted to a single-worker extraction Pipeline: an extractor is chosen by MIME type/extension, run under a panic-recovery net and a 60 s hard watchdog, its output split into chunks, and one ContentDoc written per chunk (internal/engine/engine.go:1995-2033; internal/indexer/pipeline.go:156-237, 287, 308-350).
- Chunking targets 2 KiB per chunk (2048 bytes), splitting at paragraph boundaries, then sentence boundaries, then raw byte positions; a chunk may overrun the target by at most 1.5×; inputs no larger than 1.25× the target are returned as a single chunk (internal/indexer/extractors/chunker.go:17, 34, 41).
- The per-torrent indexing toggle is exposed as CLI `swartznet index <infohash> on|off`, HTTP `POST /torrents/{infohash}/indexing {"enabled":bool}`, and GUI Downloads right-click "Start/Stop indexing"; the effect is prospective only — already-indexed chunks remain (cmd/swartznet/cmd_index.go:15-77; internal/httpapi/server.go:993-1019; internal/engine/engine.go:2405-2428).
- The pipeline keeps per-torrent extraction counters (processed/extracted/skipped/failed, keyed by lowercase infohash) that surface in engine torrent snapshots as IndexedFiles/IndexExtracted (internal/indexer/pipeline.go:44-70, 251-269; internal/engine/engine.go:2248-2253).

**Extractor registry**

- Each extractor emits plain searchable text and a `Name()` that lands in the doc's extractor field. Coverage: plaintext (all `text/*` including source code, JSON, HTML-as-raw-text); subtitle (SRT/VTT/SSA dialog only, timestamps/markup stripped); PDF (embedded text layer, no OCR); EPUB (all XHTML chapters in lexical order); DOCX (`word/document.xml` `<w:t>` runs); ODT+ODP (`content.xml` `text:p`/`text:h`); PPTX (`ppt/slides/slideN.xml` `<a:t>` in numeric slide order); RTF (control-word subset); FB2 (title + body paragraphs); MOBI/AZW/AZW3 (EXTH metadata only: title/author/publisher/description/ISBN); archives zip/tar/tar.gz (member names only, sorted, 4 MiB cap); EXIF (JPEG camera/GPS metadata); ID3 (MP3 tags); FLAC and OGG/Opus (Vorbis comments); MP4/M4A/M4B (iTunes ilst atoms); MKV/WebM (EBML Title/Tracks/Chapters/Tags); ZIM (per-article HTML→text over zstd/uncompressed clusters, max 5000 articles / 32 MiB) (internal/indexer/extractors/*.go, e.g. plaintext.go:119-143, archive.go:169-191, zim.go:499-509).

**Schema versioning and lifecycle**

- The index carries `SchemaVersion = 3` in a sentinel stored in Bleve's internal (non-searchable) metadata store under key `_swartznet_schema_version`. Opening an index dir whose sentinel disagrees (missing/unparseable counts as v0) logs `indexer.schema_rebuild`, deletes the entire directory, and recreates it empty; docs repopulate from re-added torrents (internal/indexer/indexer.go:24, 46-105; internal/indexer/schema.go:48-56).
- `DeleteTorrent(infohash)` and `DeleteContentForTorrent(infohash)` remove a torrent's index footprint; content deletion is batched query-then-delete with a fail-closed progress bound (internal/indexer/indexer.go:230-239, 846-887; internal/indexer/content.go:87-99).
- Bulk export for companion publishing walks the whole index in 1000-doc pages (`AllTorrentDocs`, `ContentDocsForInfoHash`); bulk import writes remote publishers' torrents/chunks into the same local index via IndexTorrent/IndexContent, so followed catalogues become searchable through every local path (internal/indexer/indexer.go:414-529; internal/companion/build.go:50-99; internal/companion/subscriber.go:269-305).
- GET /index/stats and the GUI Status "Local Index" card report on-disk bytes, total/torrent/content doc counts, summed corpus text bytes, and the DirBytes/CorpusTextBytes inflation ratio (internal/indexer/indexer.go:263-385; internal/httpapi/server.go:690-729).

### 2.5 Search Layer S — sn_search peer-wire protocol

Layer S is a BEP-10 (LTEP) user extension named `sn_search` that lets two peers on an ordinary piece-transfer connection exchange search queries/results, capability announcements, and RIBLT set-reconciliation of signed keyword→infohash records. Vanilla clients see only an unknown name in the LTEP `m` dict and ignore it.

**Negotiation and envelope**

- The node advertises `sn_search` in every outbound LTEP handshake (registered per-connection from the engine's PeerConnAdded callback) and records each remote peer's support plus its chosen extension id from the remote `m` dict; unsupported peers are tracked but never sent sn_search frames (internal/swarmsearch/protocol.go:15, 485-527; internal/engine/engine.go:692-711).
- Every sn_search wire message is a bencoded dict with a top-level `msg_type` integer discriminator and a `txid` uint32: 0=query, 1=result, 2=reject, 3=peer_announce, 4=sync_begin, 5=sync_symbols, 6=sync_need, 7=sync_records, 8=sync_end (internal/swarmsearch/wire.go:13-18; internal/swarmsearch/sync_wire.go:20-24).
- On seeing a capable peer, the node fire-and-forget sends one peer_announce (msg_type 3) carrying `v` (protocol version 1), `services` (64-bit bitfield), optionally `pk` (its own 32-byte ed25519 Layer-D publisher key, only when actively publishing), and optionally `endorsed` (≤10 vouched 32-byte publisher pubkeys; the cap is enforced on encode and decode, wrong-length entries are silently dropped). Sends go through a single bounded worker queue (depth 64; overflow drops) (internal/swarmsearch/protocol.go:529-617; internal/swarmsearch/wire.go:209-270).
- ServiceBits assignments are append-only, and unknown bits MUST be ignored, never rejected: bit 0 ShareLocal (answers from full local index), bit 1 ShareSwarm (answers only for active swarms), bit 2 FileHits, bit 3 ContentHits, bit 4 LayerDPublisher, bit 5 CompanionPublisher, bit 6 CompanionSubscriber, bit 7 SnippetHighlight, bit 8 Regtest (deliberately loud), bit 9 SetReconciliation (required to receive sync frames) (internal/swarmsearch/services.go:22-77).

**Query/result exchange**

- Query (msg_type 0) fields: `q` (text), `scope` (union of flags, default `"nfc"` = name/file/content), `limit`, `lang`, `min_size`, `max_size`, `not_ih` (excluded infohashes). Result (msg_type 1): `total`, `partial`, `hits` — each Hit carrying `ih` (20-byte SHA-1), optional `ih2` (32-byte BEP-52), `n` (name truncated to ~60 bytes), `s`/`l` (seeders/leechers), `sz`, `t` (indexed-at unix ts), `rank` (responder score scaled 0–1000), and `matches` (per-file: `fi` index, `fp` path, `pr` BEP-52 pieces root, `sn` snippet, `off` byte offset). Reject (msg_type 2): `code` + optional `reason` (internal/swarmsearch/wire.go:36-108).
- Inbound queries are answered against the local Bleve index via an adapter, grouping content hits into per-torrent Hit rows; failures produce a Reject with code 0=rate_limited, 1=too_expensive, 2=unsupported_scope, 3=query_too_broad, 4=shutting_down. Specifically: code 0 when the per-peer token bucket (default 5 queries/s, burst 10, runtime-configurable) is exhausted; code 4 when no searcher is attached or ShareLocal is off; code 2 when the requested scope asks for f/c hits the node lacks; code 3 when the trimmed query is under 2 characters. The per-peer result limit is clamped to 1..100, default 50 (internal/swarmsearch/handler.go:655-814; internal/swarmsearch/ratelimit.go:32-37; internal/swarmsearch/wire.go:21-27).
- Outbound `Query()` fans a bencoded query out to all "tried" peers plus up to 2 untried "feeler" peers (all supported peers when the tried table is empty), waits until every asked peer answered or the timeout (default 3 s) expires, then returns merged hits deduplicated by infohash — summed rank capped at 1000, max seeders, first non-empty name/size, union of file matches, per-hit source-peer attribution — sorted score desc then seeders desc (internal/swarmsearch/query.go:149-281, 363-429, 449-502).
- Anti-spoofing: a Result/Reject is accepted only if its txid matches a live pending query AND the sender is in that query's fan-out set; stale txids, unasked peers, and semantically-malformed results are charged misbehavior and dropped (malformed results are charged before the txid lookup) (internal/swarmsearch/query.go:81-97, 287-349).
- Merged hits from every fan-out populate a 4096-entry LRU HitCache (BIP-152-inspired state store for a planned compact short-ID encoding) (internal/swarmsearch/query.go:263-272; internal/swarmsearch/hitcache.go:23-50).

**Peer management and abuse defense (Bitcoin-Core-inspired)**

- AddrMan-style two-table PeerBook (tried max 256 / new max 1024): peers enter "new" on capable handshake, are promoted to "tried" only after correctly answering a real query, accrue Failures on timeout/reject, and are removed on disconnect; eviction is oldest-seen from new, least-recently-queried from tried (internal/swarmsearch/peerbook.go:40-251).
- A background feeler goroutine (one per engine, 30 s interval in production / 2 s in regtest, CAS-guarded against duplicates) fires a throwaway query `"__sn_feeler__"` whenever untried peers exist, giving them a promotion chance through the normal query path (internal/swarmsearch/feeler.go:17-100; internal/engine/engine.go:847-851).
- Per-peer misbehavior points: bad bencode 20, bad record signature 20, stale txid 10, unexpected/unknown message 10, malformed result 10, rate-limited 5, too-broad query 5. Crossing 100 points bans the peer locally for 24 h — banned peers are rejected at handshake and every inbound frame from them is dropped. Bans are in-memory only, survive peer disconnect, and are never gossiped (internal/swarmsearch/misbehavior.go:25-84, 174-186; internal/swarmsearch/protocol.go:500-507; internal/swarmsearch/handler.go:86-93).

**Aggregate sync (msg_types 4–8, RIBLT set reconciliation)**

- sync_begin (4) fields: `algo` (`"riblt-v1"`), `filter` (`pubkeys` list of 32-byte keys, `since` unix floor, `prefix` keyword prefix), `element_size` (32), `local_count` hint, optional `max_symbols`/`max_bytes` budgets. sync_symbols (5): `symbols` list (each `c` int32 count, `h` uint64 key-XOR, `b` 32-byte data-XOR), `done` flag, `index` = first symbol's stream position. sync_need (6): `ids`, each 32 bytes. sync_records (7): `records` (each `pk`/`kw`/`ih`/`t`/`pow`/`sig`) plus `missing` IDs the sender lacks. sync_end (8): `status`, `decoded`, `sent`, `bytes_in`, `bytes_out`, `abort_code` (internal/swarmsearch/sync_wire.go:20-139).
- All sync frames are gated on the remote having announced BitSetReconciliation (bit 9); violating peers get reject code 2 plus a misbehavior charge (internal/swarmsearch/handler.go:224-455; internal/swarmsearch/services.go:67-72).
- Responder: on sync_begin it snapshots matching records from the attached RecordSource and streams one batch of up to 100 RIBLT symbols (or immediately sync_end `"converged"` for a zero-record set); serves sync_need lookups with sync_records; tears down on sync_end. Sessions are bounded to 4 concurrent per peer (re-begin on the same txid replaces rather than counts) and any session older than 2 minutes is lazily reaped on the next inbound sync frame with a sync_end `"aborted"`; mid-session protocol violations (phase errors, symbol-index desync, budget overruns) produce sync_end `"aborted"`/`"limit_exceeded"` plus a misbehavior charge (internal/swarmsearch/handler.go:203-455, 598-619).
- Initiator: StartSync/SendSyncNeed/CloseSync/WaitSyncConverged, capability-gated; the session is registered before sync_begin is sent so a fast reply cannot race; the same (peer, txid)-keyed session map serves both directions (internal/swarmsearch/sync_start.go:49-140).
- Records arriving via sync_records are individually ed25519-verified — signature over `pk || kw || ih || t (little-endian) || pow (uvarint)` — before reaching the RecordSink; a bad signature charges 20 points and drops only that record. Each distinct publisher pubkey in an accepted frame is forwarded once to the PublisherObserver (bootstrap admission signal). PoW-threshold enforcement is delegated to the sink, not this layer (internal/swarmsearch/handler.go:457-503; internal/swarmsearch/sync_session.go:522-534).
- RecordCache: an in-memory store implementing both RecordSource and RecordSink, keyed by deterministic SHA-256 record ID, FIFO-evicted at a soft cap; the engine attaches one unconditionally with cap 100,000 records, pruned hourly with a 30-day max age (200 ms/500 ms in regtest) (internal/swarmsearch/record_cache.go:25-118; internal/engine/engine.go:56-70, 669-672, 857-869).

**Gossip intake and surfacing**

- From peer_announce: a valid non-zero 32-byte `pk` is stored on the peer's state and forwarded to the IndexerSink (wired to the Layer-D lookup as known indexer labeled `gossip:<addr>`); `endorsed` lists are routed to the EndorsementSink only when the endorser announced its own pubkey, skipping self-endorsements and all-zero keys (internal/swarmsearch/handler.go:124-192; internal/engine/engine.go:1071-1114; internal/daemon/daemon.go:206-207).
- HTTP/CLI/GUI: POST /search with `swarm:true` runs the fan-out and returns asked/responded/rejected counts plus hits; CLI `swartznet search --swarm --swarm-timeout-ms` routes through that API; GET /status reports known/capable peer counts; GET /aggregate reports record-cache kind/size/cap and the hex services mask; POST /capabilities updates the 4-field capability set at runtime (clamped); GUI Settings applies the same (internal/httpapi/server.go:554-583, 670-673, 1197-1233; internal/httpapi/aggregate.go:117-133).
- Engine-side hardening of the inbound path: sn_search frames are handled on goroutines off the torrent library's read loop (deadlock/head-of-line avoidance), payloads are copied, and admission is gated by a 256-slot semaphore plus a separate 256-slot reply-writer semaphore; overload drops frames/replies rather than queueing (internal/engine/engine.go:716-794; internal/engine/swarmadapter.go:25-41).

### 2.6 Search Layer D — BEP-44 DHT keyword index

Layer D publishes and looks up keyword→infohash mappings as BEP-44 mutable items on the mainline DHT, at target `SHA1(publisher_pubkey || keyword-salt)`; a vanilla client sees only standard BEP-44/46/51 traffic.

**Publishing**

- Every torrent whose metadata arrives is tokenised (name → up to 8 keywords) and one BEP-44 mutable item per keyword is put under `SHA1(node_pubkey || keyword)`; all entries are re-published on an hourly refresh ticker so they outlive the 2 h BEP-44 TTL (internal/dhtindex/publisher.go:29, 171-232; internal/engine/engine.go:2086).
- Keyword extraction rules: lowercase; unicode letter/digit runs only; ≥3 bytes; English stop-word and file-extension deny lists; dedup preserving first-appearance order; capped at 8 per torrent (internal/dhtindex/tokenize.go:13-124).
- Keyword value wire format (bencoded, hard-capped at the BEP-44 limit of 1000 bytes on both encode and decode): `ts` (unix), `hits` list (each `ih` 20-byte infohash, optional `n` short name, `s` seeders, `f` file count, `sz` bytes), optional `more` overflow count, optional `next_pk` continuation pubkey; a keyword whose value cannot fit under the cap is unpublishable (internal/dhtindex/schema.go:17-146).
- A persistent publish manifest at `~/.local/share/swartznet/publisher.json` (JSON, atomic tmp+rename) records per-keyword hits, LastPublished, LastError, PublishCount; a restarted node resumes publishing its full hit lists (internal/dhtindex/manifest.go:14-113; internal/config/config.go:325-327).
- Retraction: removing a torrent from the engine scrubs its infohash from every keyword entry in the manifest and persists, so the next refresh tick stops re-announcing it (internal/dhtindex/publisher.go:143-154; internal/engine/engine.go:2460-2466).
- Publisher status (total keywords, total hits, per-keyword publish counts / last publish / last error) surfaces in `swartznet status` and GET /status (internal/dhtindex/publisher.go:302-332; cmd/swartznet/cmd_status.go:134-153).

**Lookup**

- POST /search with `dht:true` (also CLI `swartznet search --dht`, GUI) fans out parallel BEP-44 gets for the query's **first token** to every known indexer pubkey; hits are merged by infohash, scored (source reputation + multi-source bonus + known-good-Bloom boost), sorted, and returned in the response's dht section (internal/dhtindex/lookup.go:274-528; internal/httpapi/server.go:588-608).
- Reputation-aware: indexers scoring below MinIndexerScore are skipped; every responding indexer's HitsReturned is recorded; per-hit (infohash→indexer) attribution is written to a SourceTracker so a later /flag demotes only the indexers that returned the flagged hash (internal/dhtindex/lookup.go:305-313, 415-418, 458-466).
- Known-indexer set: the node's own pubkey is auto-added as "self"; peers gossiped via sn_search peer_announce are added via the gossip sink; bootstrap-admitted anchor publishers are added via AddIndexer; AddIndexerHex validates 64-hex keys (internal/engine/engine.go:1054-1058, 1102-1110; internal/dhtindex/lookup.go:206-244).

**Pointer and crawl primitives**

- BEP-46 pointer put/get: PutInfohashPointer publishes a signed mutable item `{"ih": <20 bytes>, "ts": <unix>}` under any ≤64-byte salt, failing closed if the put reached zero DHT nodes; GetInfohashPointer(/Info) fetches and validates it, the Info variant surfacing the publisher timestamp for staleness policy; inbound values are size-bounded to the 1000-byte BEP-44 cap before decoding (internal/dhtindex/dht.go:130-254).
- PPMI (per-publisher pointer mutable item): PutPPMI/GetPPMI store/fetch a small bencoded `{ih, commit?, topics?, ts, next_pk?}` value at the fixed salt `SHA256("snet.index")` per publisher — one shared salt for all publishers, so discrimination happens at the pubkey; Lookup.Query can optionally resolve PPMIs first, falling back to legacy per-keyword gets per publisher (internal/dhtindex/ppmi.go:29-162; internal/dhtindex/lookup.go:315-340).
- BEP-51 crawl primitives: SampleInfohashes issues one sample_infohashes query (returning samples, interval hint, num, merged v4/v6 neighbour nodes); CrawlOnce fetches each sample's metainfo, classifies `snet.pubkey` signatures, and forwards signed publishers (valid AND invalid signatures) to a sink for admission policy (internal/dhtindex/crawler.go:43-84; internal/dhtindex/crawler_tick.go:58-112).
- CLI `swartznet crawl-probe --addr host:port [--target hex] [--json]` runs a one-shot BEP-51 probe from a throwaway loopback DHT server, printing samples/interval/num/nodes — no daemon or state needed (cmd/swartznet/cmd_crawl_probe.go:30-142). The standalone `cmd/dht-smoke` binary performs real BEP-44 keyword put/get round-trips against the live DHT using the same putter/getter (cmd/dht-smoke/main.go:111-131).

**Modes**

- Privacy: `--no-index` and DisableDHTPublish suppress the keyword Publisher worker (leech-only Layer D) while keeping the lookup, pointer getter, AND pointer putter alive — companion pointer publication is an explicit opt-in governed by CompanionDir, not by DisableDHTPublish (internal/engine/engine.go:995-1023).
- Regtest substitutes accelerated time constants for both publishers (5–10 s refresh, 100 ms min-interval) so scenario tests run in seconds; never in production (internal/dhtindex/publisher.go:56-74; internal/companion/publisher.go:83-95).

### 2.7 Companion indexes and aggregate B-tree indexes

**Companion content-index cycle (BEP-46 pointer pattern)**

- Publisher worker: on start and hourly thereafter it walks the local Bleve index, writes `<CompanionDir>/swartznet-content-index-<pk12>-v1.json.gz` plus `companion.torrent` (both atomic writes), seeds the torrent through the engine, and puts a BEP-46 pointer to the new infohash at salt `"_sn_content_index"` (constant SaltContentIndex; the pointer target is `SHA1(publisher_pubkey || salt)`) (internal/companion/publisher.go:23, 97-344; internal/companion/torrent.go:45-78; internal/daemon/daemon.go:133-146).
- Manual refresh via POST /companion/refresh (and GUI button) is throttled to one attempt per MinInterval (1 min default); throttled calls return HTTP 429 (internal/companion/publisher.go:216-234; internal/httpapi/companion.go:93-105).
- Snapshot file format (gzipped JSON, FormatVersion 1): top-level `{version:1, format:"swartznet-content-index", publisher:<64-hex pubkey>, generated_at:<unix>, torrents:[...]}`; the file begins with the exact magic prefix `{"version":1,"format":"swartznet-content-index"`. Each torrent record: `infohash` (40-char lowercase hex), `name`, `size`, `added_at`, optional `files` (each `index`, `path`, `size`, `mime`, `extractor`, optional `chunks` of `{text, offset}`). Subscribers refuse unrecognised versions and use `generated_at` to skip already-imported snapshots (internal/companion/types.go:3-121).
- Subscriber worker: for each followed publisher pubkey, hourly (plus immediately on Follow) it resolves the BEP-46 pointer, downloads the companion torrent through the engine, gunzips/decodes the JSON, and imports every torrent record and content chunk into the local Bleve index, making foreign catalogues searchable via all local search paths (internal/companion/subscriber.go:160-308, 436-504; internal/daemon/daemon.go:149-178).
- Engine-side fetch guards: FetchCompanionTorrent adds the infohash, waits for metadata, requires exactly one file, rejects a declared length over 32 MiB before requesting pieces, rejects unsafe file names, polls to completion, and returns the on-disk path (internal/engine/engine.go:94, 1295-1376).
- Management surface: GET /companion (publisher status + per-follow sync results); POST /companion/follow and /companion/unfollow take a 64-hex pubkey + label, mutate the worker, and atomically rewrite the follow file. Daemon startup loads `companion-follows.json` (JSON array of `{pubkey,label}`): a missing file is fine, a file over 1 MiB is rejected wholesale, malformed rows are skipped with a warning (internal/httpapi/companion.go:79-155; internal/daemon/follows.go:48-93).

**Aggregate B-tree index-torrent format (signed, PoW-protected)**

- Record: `pk` (32-byte ed25519 publisher key), `kw` (lowercased UTF-8 keyword, ≤64 bytes, non-empty), `ih` (20-byte infohash), `t` (unix), `pow` (hashcash nonce), `sig` (64-byte ed25519 over `pk || kw || ih || t (little-endian uint64) || pow (uvarint)`); bencoded with those short field names, hard ceiling 256 bytes per encoded record (internal/companion/btree.go:52-113, 170-192).
- Every page is exactly one BitTorrent piece; piece size must be in [16384, 4 MiB]. Pages start with the 6-byte magic `SNAGG\0` followed by a fixed 16-byte header; page kinds are 0x00 root, 0x01 interior, 0x02 leaf, 0xFF trailer (internal/companion/btree.go:22-44; internal/companion/build_btree.go:41-50, 73-76).
- BuildBTree deterministically packs sorted signed records into fixed-size pages: root at piece 0, BFS level layout, leaves last-but-one, signed trailer as the final piece; the file length is `NumPages × PieceSize` (pages zero-padded) and the builder returns the bytes plus a SHA-256 tree fingerprint computed independently of piece-size choice — this fingerprint is the value carried in the PPMI `commit` field (internal/companion/build_btree.go:111-297).
- Trailer payload is fixed at 162 bytes, little-endian scalars, in order: trailer_version (1), pubkey (32), seq (8), created_ts (8), root_piece_index (4), num_pages (4), num_records (8), min_pow_bits (1), tree_fingerprint (32), publisher_sig (64 — ed25519 over all preceding fields in that canonical order) (internal/companion/btree.go:438-478).
- Reader: OpenBTree verifies the trailer signature before anything else; Find(prefix) walks root→leaves fetching only pages overlapping the prefix range, silently dropping records with bad ed25519 signatures or insufficient hashcash PoW; VerifyFingerprint optionally re-derives the full fingerprint (internal/companion/read_btree.go:66-168, 306-351).
- Hashcash PoW: MineRecordPoW finds a nonce giving ≥N leading zero bits of SHA256(sig-message), refusing N>40; the default writer/reader difficulty is 20 bits; SignAndMineRecord enforces mine-then-sign ordering; readers verify at one hash per record (internal/companion/pow.go:39-93; internal/companion/btree.go:48; internal/companion/read_btree.go:389-399).
- Offline CLI: `swartznet aggregate build --out F [--in JSONL] [--key] [--seq] [--piece-size] [--pow-bits]` signs and packs; `aggregate inspect FILE` prints trailer metadata; `aggregate find [--verify] FILE PREFIX` runs a prefix query — all without daemon or network (cmd/swartznet/cmd_aggregate.go:20-160).
- Distribution seam with Layer S: the engine mints per-keyword Aggregate records (currently PoW=0) into the swarmsearch RecordCache on every torrent add, so sn_search sync sessions can distribute them (internal/engine/engine.go:243-283).

### 2.8 Identity, signing, trust, and reputation

**Publisher identity (ed25519 keypair)**

- On first run the node generates an ed25519 keypair and persists it as the raw 64-byte private key at `identity.key` (file mode 0600, parent directory 0700). On subsequent runs it loads that file and **refuses to proceed — never silently regenerates** — if the file exists but has wrong permissions, wrong size, is a directory, or its public half does not match its seed (internal/identity/identity.go:33-98).
- The identity backs everything publisher-shaped: BEP-44 DHT puts are signed with it, the node registers its own pubkey as Layer-D indexer "self", the `sn_search` peer_announce `pk` field carries it, and Aggregate LocalRecords are minted/signed with it. Losing the key severs publisher reputation permanently. Identity load failure is non-fatal: the node still downloads and searches locally, it just cannot publish (internal/engine/engine.go:961-977,248-277).
- `swartznet create --sign [--identity <path>]` signs the created `.torrent` and prints `Signing with identity <hex>`. An explicit `--identity` path is load-only — a missing file is a hard error, so a torrent is never orphaned under a fresh untrusted key; only the default XDG path may auto-create a key. `--identity` without `--sign` is a usage error. The same load-only rule applies to `swartznet aggregate build --key` (cmd/swartznet/cmd_create.go:50-104; cmd/swartznet/cmd_aggregate_build.go:110-146).

**Infohash-preserving `.torrent` signing**

- Signing adds two optional top-level bencode fields to the metainfo dict: `snet.pubkey` (32 bytes) and `snet.sig` (64 bytes, ed25519 signature over the payload `"SN-TORRENT-V1|" || SHA1(info dict)`). The info-dict bytes are untouched, so the infohash is preserved and vanilla clients (which ignore unknown top-level keys) are unaffected — signed and unsigned twins share one swarm. Re-signing replaces existing snet fields. File writes are atomic (tmp + rename, mode 0644). Formal spec: docs/11-signing-protocol.md (internal/signing/signing.go:85-141).
- When a `.torrent` file is added, the signature is verified automatically: valid → the torrent handle records `SignedBy` (64-char lowercase hex pubkey); invalid → a warning is logged but the torrent is still added, unsigned; absent → silent (not-signed is normal). Magnet adds always get `signed_by=""`. `SignedBy` is persisted in the session store and restored across restarts without re-verification (internal/engine/engine.go:1199-1231,1616,1841).
- `SignedBy` is indexed in Bleve as a lowercase keyword field `signed_by`; `swartznet search --signed-by <hex>` filters local results by signer, and a signed-by-only query with empty text is valid (internal/indexer/schema.go:36; internal/indexer/indexer.go:696-724; cmd/swartznet/cmd_search.go:51-67).

**Publisher trust list**

- `swartznet trust list|add|remove` (aliases `ls`/`rm`; `--file` path override; `--json` on list) manages the allowlist entirely offline against `trust.json` — no daemon round-trip. `add` is idempotent and relabels an existing entry; `remove` is idempotent; `list` prints a PUBKEY/LABEL table or a "(no trusted publishers yet …)" hint (cmd/swartznet/cmd_trust.go:18-157).
- A torrent signed by a trust-listed pubkey is auto-confirmed into the known-good Bloom filter the moment its metadata arrives — without waiting for download completion (internal/engine/engine.go:2099-2114).
- Torrent snapshots carry `SignedBy` and `TrustedPublisher` through `GET /torrents` (JSON `signed_by`/`trusted_publisher`) so all frontends can badge signed/trusted torrents (internal/engine/engine.go:2219-2247; internal/httpapi/server.go:104-105).
- `trust.json` is rewritten atomically on every Add/Remove (internal/trust/trust.go:159-179).

**Reputation, Bloom filter, and feedback attribution**

- Per-indexer Bayesian reputation: every Layer-D query records `HitsReturned` for each responding indexer pubkey; indexers whose derived score falls below the configurable `MinIndexerScore` (config default 0 = gate disabled) are skipped before the DHT fan-out; merged hit ranking folds in average source reputation, a multi-source bonus, and Bloom-filter membership (internal/dhtindex/lookup.go:301-313,486-528; internal/config/config.go:195-198).
- Known-good Bloom filter (sized for ~1M items at 1% false-positive rate, ~1.2 MB): a torrent's infohash is auto-added when its download completes (background goroutine with a 24h cap, cancelled on remove/shutdown). Bloom membership marks a lookup hit `BloomHit`, adds +0.25 to its score, and sorts Bloom hits above all others (internal/engine/engine.go:1949-1986; internal/dhtindex/lookup.go:448-474,518-520; docs/05-integration-design.md:316-322).
- A SourceTracker (in-memory LRU, default 10,000 infohashes) records which indexer pubkeys returned each hit during Layer-D lookups, so user feedback targets exactly the responsible indexers (internal/reputation/sources.go:24-158; internal/dhtindex/lookup.go:458-466).
- Confirm semantics: adds the 20-byte infohash to the Bloom filter; the GUI additionally calls `RecordConfirmed` for every pubkey attributed to that hit. Flag semantics: demotes (`RecordFlagged`) **only** the attributed indexer pubkeys, then forgets the attribution; with zero attribution it **fails closed** and demotes nobody (the GUI shows an explanatory dialog; the API returns ok with zero flagged) (internal/httpapi/server.go:818-889; internal/gui/search.go:411-466).
- `swartznet flag <infohash>` / `swartznet confirm <infohash>` POST to the running daemon (default `localhost:7654`, `--api-addr` override, 5s timeout), validate 40-hex input, and print `flagged:`/`confirmed:` on success (cmd/swartznet/cmd_flag.go:22-96).
- Curated seed list: at engine startup `seeds.json` (`{"version":1,"seeds":[...]}`) is imported, giving each pubkey a +0.45 score bonus that decays with a 90-day half-life (cold-start bootstrap). A missing file is fine; bad entries are skipped with per-entry errors; any version other than 1 is rejected wholesale (internal/reputation/reputation.go:80-91,385-423; internal/engine/engine.go:910-918).
- Cold-start Bootstrap marks admitted anchor pubkeys as seeded with the same decaying bonus, exempts anchors from the `MaxTrackedPublishers` cap (default 100), and applies reputation thresholds for admission: 0.3 for crawl candidates, 0.5 for "strong endorsers", default endorsement threshold 3 (internal/daemon/bootstrap.go:44-72,401-484).
- Persistence: the Bloom filter and reputation tracker are saved atomically only at engine Close; an empty path yields a valid in-memory-only instance whose Save is a no-op (internal/engine/engine.go:2516-2527; internal/reputation/reputation.go:140-161; internal/reputation/bloom.go:97-126).

### 2.9 HTTP API and embedded web UI

**Server lifecycle and hardening**

- The API is a loopback-only, unauthenticated HTTP control plane defaulting to `localhost:7654`; it is also the IPC surface the CLI subcommands (`search`, `status`, `flag`, `confirm`, `files`, `index`) use to talk to a running `swartznet add` daemon. It holds no engine/companion imports — every collaborator is a narrow interface wired by the daemon, and **every collaborator is optional**: any handler whose collaborator is nil returns 503 "X not configured", so a partially wired daemon (`--no-index`, `--no-dht`) serves a coherent degraded API (internal/httpapi/server.go:196-225).
- Start binds synchronously (so the effective address of a `:0` bind is queryable), then serves in a goroutine. A non-loopback bind logs a loud "API is UNAUTHENTICATED" warning but still binds (operators may front their own auth). Stop is idempotent and the server is reusable across Start/Stop cycles. HTTP timeouts: ReadHeader 2s, Read 5s, Write 30s, Idle 60s; MaxHeaderBytes 256 KiB (internal/httpapi/server.go:237-262,284-393).
- CSRF/DNS-rebinding guard on every non-GET/HEAD/OPTIONS request: the Host header must be loopback (127.0.0.0/8, ::1, or literal `localhost`, case-insensitive, port and IPv6 brackets stripped); if an Origin header is present its host must be loopback, otherwise a present Referer's host must be loopback (Origin checked first). Fails closed with 403. curl/CLI requests (no Origin/Referer, loopback Host) are unaffected; reads are always exempt (internal/httpapi/csrf.go:39-107).
- Every request body is capped at 1 MiB; overflow surfaces as a 400 JSON-decode failure. Middleware order: body cap wraps the CSRF guard wraps the mux (internal/httpapi/bodylimit.go:12-28; internal/httpapi/server.go:348-357).

**Search endpoint (the three-layer seam)**

- `POST /search` body `{q, limit, swarm, dht, swarm_timeout_ms, dht_timeout_ms, signed_by, highlight}`. Always runs Layer L (when the index is wired); optionally fans out to Layer S (`swarm:true`) and Layer D (`dht:true`). Response: `{local:{total,hits[]}, swarm?:{asked,responded,rejected,hits[],error?}, dht?:{indexers_asked,indexers_responded,hits[],error?}}`. A local-layer failure fails the whole request with 500; swarm/DHT failures are reported inline as error strings with HTTP 200. `signed_by` (64-hex pubkey) filters Layer L only. `highlight:true` adds `<mark>`-wrapped Bleve fragments per hit (internal/httpapi/server.go:396-613).
- Request hygiene: `q` required (400 if empty), capped at 1024 bytes (400 above); `limit<=0` defaults to 50, capped at 500. Per-layer timeouts default swarm 2s / DHT 5s, both clamped to 30s max; the handler context deadline is timeout+500ms grace (internal/httpapi/server.go:127-158,512-519).

**Status and introspection**

- `GET /healthz`: `{ok:true, version}`; version is a package-global atomic string the daemon sets from its version at startup (internal/httpapi/server.go:1239-1262).
- `GET /status`: aggregated snapshot — `local{indexed,doc_count}`, `swarm{known_peers,capable_peers}`, `publisher{pubkey?,total_keywords,total_hits,keywords[]}` (per-keyword hits_count, last_published RFC3339 UTC omitted when zero, publish_count, last_error), `dht{good_nodes,nodes}` (block omitted entirely when DHT is disabled), `bloom{bit_size,hash_functions,population_bits,estimated_items}`, `reputation{known_indexers, top_indexers}` truncated to 10 (internal/httpapi/server.go:615-795).
- `GET /index/stats`: `{dir_bytes,doc_count,torrent_count,content_count,corpus_text_bytes,inflation_ratio}` — the index-size-per-corpus measurement; 503 when index absent; scans every content doc, so intended for human-cadence polling only (internal/httpapi/server.go:690-727).
- `GET /aggregate`: v0.5 Aggregate-track introspection — `{ppmi_enabled, known_indexers, indexers[{pk,label}], record_source_kind("cache"|"custom"|""), record_cache_size, record_cache_max, services (16 lowercase hex chars, big-endian, no 0x), bootstrap?{anchors,admitted,pending}}`; `bootstrap` omitted when no probe is wired (internal/httpapi/aggregate.go:25-145).

**Torrent and config control**

- `POST /torrent {uri}` adds a magnet URI and returns `{ok,infohash}` immediately (metadata fetch is async); 400 on add error (internal/httpapi/server.go:891-927).
- `GET /torrents`: per-torrent infohash, name, size, bytes completed/missing, progress, file count, peer counts (active/half_open/pending/total), seeders, paused, status string, indexing flag, indexed_files/index_extracted (omitempty), queued, download/upload rates, signed_by/trusted_publisher (omitempty) (internal/httpapi/server.go:83-106,954-968).
- `POST /torrents/{ih}/pause`, `POST /torrents/{ih}/resume` (both idempotent), `DELETE /torrents/{ih}` (removes the torrent, **leaves on-disk files**). All validate a 40-hex path infohash (400), return 503 when the controller is absent, map engine errors to 400, and return `{ok,infohash,action}` (internal/httpapi/server.go:970-986,1171-1195).
- `POST /torrents/{ih}/indexing {enabled:bool}` flips the per-torrent indexing toggle (also exposed as CLI `swartznet index` and a web-UI per-torrent button) (internal/httpapi/server.go:988-1018).
- `GET /torrents/{ih}/files` lists `{index,path,display_path,length,bytes_completed,progress,priority}` per file; `POST /torrents/{ih}/files/{index}/priority {priority:"none"|"normal"|"high"}` sets one file's priority; the index is parsed strictly (trailing garbage/negatives → 400) (internal/httpapi/server.go:68-78,1020-1088).
- `GET/POST /config/rate-limit {upload_bps,download_bps}` and `GET/POST /config/queue {max_active_downloads}`: zero means unlimited; POST always sets **both** rate fields (no leave-unchanged semantics) and replies with the fresh GET body (internal/httpapi/server.go:1090-1169).
- `GET/POST /capabilities`: read/write the `sn_search` sharing levels `{share_local,file_hits,content_hits,publisher}`; POST clamps `share_local` to 0..2 and the others to 0..1, replaces the whole struct, and echoes the post-clamp values (internal/httpapi/server.go:929-952,1197-1233).
- `POST /confirm {infohash}` and `POST /flag {infohash}`: 400 unless exactly 40 hex chars, 503 when the bloom filter / source tracker is unwired; semantics per §2.8 (internal/httpapi/server.go:818-889).
- Companion endpoints: `GET /companion` returns publisher state (last_refresh, last_infohash, last_error?, published_count, pubkey_hex?) plus the subscriber list (per-followed pubkey_hex, label?, last_sync_at?, last_error?, torrents_imported, content_imported, generated_at?, pointer_infohash?); `POST /companion/refresh` triggers an out-of-band publish, mapping any error to HTTP 429 (so UIs can show the min-interval throttle); `POST /companion/follow {pubkey:64-hex,label?}` and `POST /companion/unfollow {pubkey}` mutate the persisted follow list (bad pubkey → 400, controller error → 500); all 503 when no companion controller (internal/httpapi/companion.go:19-155).

**Embedded web UI**

- `GET /{$}` serves `index.html` and `GET /static/` serves css/js from a go:embed FS compiled into the CLI binary; API routes are registered first so they win over the catch-all; if the embed sub-FS fails, the daemon logs a warning and runs API-only. Six tabs: Search, Add torrent, Downloads, Companion, Status, Sharing (internal/httpapi/server.go:335-346; internal/httpapi/web/embed.go:17-25).
- Search tab: swarm/DHT checkboxes, limit input (UI max 100), optional publisher-pubkey filter, always sends `highlight:true`; renders three labelled layer sections with per-layer asked/responded/rejected counts and inline layer errors; every hit gets confirm and flag buttons (flag asks for confirmation); clicking a hit's signed-by badge re-runs the search filtered to that publisher; highlight fragments (max 2) are injected via innerHTML, relying on Bleve pre-escaping (web/static/app.js:152-379).
- Keyboard shortcut: `/` or Ctrl/Cmd+K jumps to the Search tab and focuses+selects the query input, ignored while typing in another input (web/static/app.js:41-60).
- Downloads tab polls `GET /torrents` every 2s while visible: progress bar, secondary indexing-progress bar (indexed_files/files with an "N with text" extractor count, shown only when indexing is on and the file count is known), down/up rates, signed badge (star for trusted publisher, check otherwise), pause/resume/remove (remove confirms and notes files stay on disk), files modal with Select All / Deselect All (serial per-file priority POSTs), per-torrent index toggle; any control action triggers an immediate re-poll (web/static/app.js:597-790).
- Status tab polls `/status` + `/index/stats` + `/torrents` + `/aggregate` every 4s while visible; the three auxiliary fetches swallow errors so older daemons missing an endpoint degrade to fewer cards; the DHT card renders only when the response has a `dht` block (web/static/app.js:410-574).
- The UI polls `/healthz` every 5s to drive a connected/offline badge (web/static/app.js:130-150).

### 2.10 Native GUI

**Process and configuration**

- The GUI binary boots a full daemon (engine + indexer + companion pub/sub + optional HTTP API) exactly like the CLI, then presents five tabs — Downloads, Search, Status, Companion, Settings — that call daemon subsystems directly in-process, with no HTTP round-trip (cmd/swartznet-gui/main.go).

**Window, tray, and shell behavior**

### 2.12 Design constraints of record (from the BEP drafts and integration design)

Any rebuild MUST honor the following as hard constraints; they are the project's load-bearing contracts, not preferences.

- **Mainline compatibility is absolute.** No new reserved handshake bit, no new DHT verb, no new UDP port. A vanilla BitTorrent client interacting with a SwartzNet node MUST observe only standard BEP-3/5/9/10/44 traffic — the only novelty visible to it is one ignorable name (`sn_search`) in the LTEP `m` dictionary, and BEP-44 items indistinguishable from anyone else's (docs/04-bep-extension-points.md:1100-1171; CLAUDE.md).
- **The wire-compat matrix (docs/05-integration-design.md §8) MUST pass in all four directions:** (1) a vanilla client downloads from us receiving zero `sn_search` frames; (2) we download from vanilla swarms without advertising `sn_search` to peers that didn't advertise it; (3) the DHT stays healthy for non-participants; (4) two SwartzNet clients negotiate search, a mismatched-scope query gets reject code 2, publishers cross-register pubkeys via peer_announce `pk` gossip, and unknown fields are tolerated for forward compatibility (docs/05-integration-design.md:637-675).
- **`sn_search` frames go only to peers that advertised the extension.** The protocol comprises msg_type 0 query, 1 result, 2 reject (5 defined codes), 3 peer_announce, and 4–8 Aggregate set-reconciliation (sync_begin/symbols/need/records/end, Rateless IBLT). Sync frames are gated on services bit 9; peers without the bit MUST receive reject code 2 for them; per-session `max_bytes` budgets MUST be enforced with a `limit_exceeded` abort; protocol violations tear the session down with a terminal sync_end plus a misbehavior charge (docs/06-bep-sn_search-draft.md:95-172).
- **Capability negotiation uses a 64-bit `services` bitfield** in peer_announce (bits 0–9 defined: ShareLocal, ShareSwarm, FileHits, ContentHits, LayerDPublisher, CompanionPublisher, CompanionSubscriber, SnippetHighlight, Regtest, SetReconciliation). Unknown bits MUST be ignored, never rejected; absence of peer_announce means services 0 and the peer is still answered (docs/06-bep-sn_search-draft.md:100-138,269-283).
- **Layer-D wire formats are fixed by spec.** Legacy: one BEP-44 mutable item per (pubkey, keyword) — salt = lowercased UTF-8 keyword, target = SHA1(pubkey||salt), value = `{ts, hits[{ih,n,s,f,sz}], more, next_pk}` ≤1000 bytes, shard spill to salts `keyword#1`, `#2`… with root `more:1`, hourly refresh against the 2h BEP-44 expiry. PPMI (v0.5+): one item per publisher at the fixed double-hashed salt SHA256("snet.index") with `v = {ih, commit, topics?, ts, next_pk}` where the real keyword records live in a signed SNAGG B-tree companion torrent whose canonical-record fingerprint is bound by `commit` (docs/07-bep-dht-keyword-index-draft.md:124-238; docs/05-integration-design.md:325-369).
- **Lookup semantics:** the searcher tokenizes exactly as publishers do, picks the most distinctive token, fans out BEP-44 gets across known indexer pubkeys in parallel, verifies each signature, and merges hits by infohash weighted by per-pubkey reputation; a single-indexer error MUST NOT abort the lookup; PPMI resolves first with legacy per-keyword fallback (docs/07-bep-dht-keyword-index-draft.md:240-259).
- **PPMI migration contract:** v0.5 dual-writes PPMI + legacy items and dual-reads; v0.6 is planned as PPMI-only writes with a deprecation notice; v0.7 removes the legacy reader; readers MUST retain legacy read compatibility for at least 12 months (docs/research/PROPOSAL.md:322-357; docs/research/SPEC.md:562-563).
- **Signing preserves the infohash.** `snet.pubkey`/`snet.sig` are top-level metainfo fields over `"SN-TORRENT-V1|" || SHA1(info dict)`; signed and unsigned twins MUST share one swarm (docs/11-signing-protocol.md:126-215).
- **Docs 06 (`sn_search`), 07 (DHT keyword index), and 11 (signing) are self-contained normative specs** sufficient to produce a wire-compatible peer in any language; the Go code is explicitly the reference implementation. Doc 05 is the architecture synthesis; any wire-format change MUST keep these specs in sync (docs/README.md:16-36).
- **Layer isolation:** Layer L (local Bleve) never touches the wire, Layer S never touches Bleve internals, Layer D never touches the HTTP API; each layer keeps its own response type and the seam is reconciled only at the httpapi boundary (docs/05-integration-design.md; CLAUDE.md).
- **MPL discipline:** anacrolix/torrent is MPL-2.0 (file-level copyleft); integration MUST use extension APIs only (callbacks, `LocalLtepProtocolMap.AddUserProtocol`, direct DHT library access), never patches to the vendored library, preserving redistribution options; first-party files stay Apache-2.0 (CLAUDE.md; THIRD_PARTY_LICENSES:1-11).
- **Identity is never regenerated implicitly**, and `--no-index` MUST cascade: Bleve never opens, the Layer-D keyword publisher is disabled, and the Publisher capability bit is zeroed (the node still subscribes/fetches but contributes nothing) (internal/identity/identity.go:33-98; docs/05-integration-design.md:131).
- **The extension-name prefix is `sn_`** (chosen because `lt_` is historically libtorrent's); the peer handshake v-string identifies the client as SwartzNet (docs/04-bep-extension-points.md:208-228,1208-1223).

### 2.13 Planned but unbuilt / deliberately rejected (from project history)

**Deliberately rejected — a rebuild must not resurrect these:**

- Alternative engines: libtorrent (scored 6.5), Transmission (2), rqbit (5), WebTorrent (3) were evaluated and rejected in favor of anacrolix/torrent (9.5) on extension-API, piece-verify-hook, BEP-44-access, and license grounds (docs/01-torrent-clients-comparison.md:589-677).
- Tribler-style flood queries to random peer subsets (its 20-random-peer RemoteSelect model): rejected because "decentralization without a metadata location mechanism means flooding random subsets" — SwartzNet integrates with the DHT instead. Tribler's engine/search-overlay separation and signed-metadata ideas were kept (docs/02-tribler-deep-dive.md:517-627).
- Any new reserved bit, DHT verb, or UDP port; any patch to the MPL-2.0 vendored library — both permanently rejected as violating the constraints in §2.12.
- Immediate BEP standardization: the recorded strategy is ship in our client first, publish our own specs, obtain a second live-swarm-tested implementation, and only then submit a BEP (docs/04-bep-extension-points.md:1208-1223).

**Consciously deferred — planned but unbuilt as of this spec:**

- PPMI migration phases 2–3: v0.6 PPMI-only writes + deprecation notice, v0.7 legacy-reader removal (v0.5 dual-write/dual-read is what shipped) (docs/research/PROPOSAL.md:322-357).
- `sn_addr` address gossip with an addrv2-style network-id byte (from the Bitcoin-Core lessons adoption list; the AddrMan-style tried/new peer book itself shipped) (docs/10-bitcoin-lessons.md:901-923).
- Delta companion indexes (publish diffs instead of full index snapshots) (docs/10-bitcoin-lessons.md:901-923).
- Full BIP-152-style short-ID result dedup — only partially realized as the LRU hit cache (docs/10-bitcoin-lessons.md:901-923).
- From the v1-blocker action table: a `CompactMode` knob, SOCKS5 proxying for the BEP-44 put path, and the DSybil heavy-tail lookup heuristic remain unimplemented (other items from that table — 1 put/key/hour cap, seed-weight decay, THIRD_PARTY_LICENSES, next_pk schema field — shipped) (docs/09-v1-blocker-research.md:379-401).
- From the P2P-search survey's staged plan: Phase 3 (optional encrypted index) and Phase 4 (ML/semantic search extras) were never started; Phases 1–2 (keyword→infohash DHT index; reputation + local filtering) are the shipped design (docs/03-p2p-search-protocols.md:894-982).
- The hardcoded Layer-D seed pubkey list is deliberately empty in v1 (discovery relies on self-pubkey, peer_announce gossip, user-supplied keys, and Aggregate bootstrap) (docs/07-bep-dht-keyword-index-draft.md:261-279).

## 3. Inputs, outputs, and data models

All persistent state lives under a single **share root**, resolved in this order: `$XDG_DATA_HOME/swartznet`, else `$HOME/.local/share/swartznet`, else `./swartznet-state` (internal/config/config.go:442-450). Every path below is relative to that root unless stated otherwise. All state-file writes are atomic (`.tmp` + rename) unless noted.

### 3.1 On-disk state (every file the program reads/writes: path, format, mode, when)

**Identity, trust, and reputation**

- `identity.key` — raw 64-byte ed25519 private key; the public key occupies bytes [32:64] and is re-derived from the seed and verified on every load. File mode must be exactly 0600 (the loader rejects any other mode); parent directory created 0700. Auto-generated on first use, but only when the path is the XDG default — an explicitly configured path that is missing is an error, never regenerated implicitly. Read at daemon start, `create --sign`, and `aggregate build` (internal/identity/identity.go:18,80-96; cmd/swartznet/cmd_aggregate_build.go:115-146).
- `trust.json` — publisher allowlist: JSON array `[{"pubkey":"<64 lowercase hex>","label":"..."}]`, pretty-printed 2-space indent, sorted by pubkey, mode 0600. Rewritten on every `trust add`/`trust remove` mutation (CLI and GUI); read at daemon start and by `trust list` (internal/trust/trust.go:34-41,161-179).
- `reputation.json` — per-indexer reputation tracker: `{"records":{"<pkhex>":{"hits_returned","hits_confirmed","hits_flagged","first_seen","last_updated","seeded_at"(omitempty),"seed_label"(omitempty)}}}`, indent-2 JSON, mode 0600. Read at start, saved on engine Close (internal/reputation/reputation.go:30-57,95-103).
- `seeds.json` — read-only curated indexer seed list `{"version":1,"seeds":[{"pubkey":"<hex>","label":"<name>"}]}`; version-gated, pubkeys re-normalized to lowercase via decode/re-encode; a missing file is not an error. Seeded entries receive a +0.45 reputation bonus decaying with a 90-day half-life (internal/reputation/reputation.go:359-423; internal/config/config.go:180-188).
- `known-good.bloom` — spam-resistance Bloom filter, custom binary format, little-endian: magic `"SBLM"` (4 bytes) + version u16 (=1) + k u16 + m u64 + bitsLen u64 + bitsLen×u64 bitset words; bitsLen must equal exactly `(m+63)/64`; `m==0` or `k==0` is rejected. Mode 0600; read at start, saved on engine Close and mutated by confirm actions (internal/reputation/bloom.go:44-49,252-314).

**Publishing and companion index**

- `publisher.json` — Layer-D per-keyword publish manifest: JSON `{"entries":{"<keyword>":{"hits":[KeywordHit],"last_published":RFC3339,"last_error"?,"publish_count":int}}}`, mode 0600; updated after each publish run (internal/dhtindex/manifest.go:28-47).
- `companion-follows.json` — followed-publisher list: JSON array `[{"pubkey":"<64-char hex ed25519>","label"(omitempty)}]`; read at daemon start with a 1 MiB size cap; written mode 0600 on every follow/unfollow. Format is owned by the daemon package, not internal/companion (internal/daemon/follows.go:14-31; internal/daemon/adapters.go:218-246).
- `companion/` — companion publisher artifacts, both mode 0600: `swartznet-content-index-<first-12-hex-of-pubkey>-v1.json.gz` (generic name `swartznet-content-index-v1.json.gz` when no pubkey) = gzipped JSON index snapshot (format in §3.2), plus `companion.torrent` = the wrapping single-file v1 metainfo. Rewritten on each companion refresh (internal/companion/types.go:16-35; internal/companion/torrent.go:58-118).

**GUI settings**

- `config.json` — GUI-persisted config overrides: JSON object with exactly two optional fields `{"data_dir":string,"index_dir":string}` (deliberately narrow whitelist), pretty-printed, mode 0644. Read at GUI startup (missing file OK; malformed JSON is an error), written by the Settings tab (internal/config/config.go:370-440).
- Fyne preferences under app ID `net.swartznet.gui` (Fyne's own config dir, e.g. `~/.config/fyne/net.swartznet.gui/preferences.json`): keys `window.width`/`window.height` as floats (internal/gui/app.go:59-63,153-156).

**Torrent data and session (under `data/`, i.e. DataDir, created 0755 by config.Validate)**

- Downloaded content is written under DataDir; torrents created with `--seed` are seeded in place under their original content root instead (session records `data_path` for these).
- `data/session.json` — open-torrents manifest, version 1: `{"version":1,"torrents":[{infohash (40-hex), added_via: magnet|file|infohash|metainfo, magnet_uri?, torrent_file? (basename under torrents/), paused?, indexing, queue_order?, signed_by?, data_path? (seed-from parent dir), content_name? (real on-disk basename, decoupled from info.Name)}]}`; entries sorted by queue_order then infohash; entries whose infohash is not exactly 40 chars are dropped on load. Mode 0644; rewritten on every add/remove/pause/resume/set-indexing (internal/engine/session.go:42-121).
- `data/torrents/<infohash>.torrent` — byte-exact copy of the original .torrent (preserving `snet.*` signing fields); for magnet adds, a re-marshalled metainfo written after metadata arrives. Mode 0644; read on session restore (internal/engine/session.go:205-235).
- `data/.torrent.db` / `data/.torrent.bolt.db` — anacrolix piece-completion databases, created implicitly by the embedded library.

**Full-text index (under `index/`, i.e. IndexDir)**

- Bleve scorch index directory (`index_meta.json`, `store/*.zap`, `store/root.bolt`); existence detected via `IndexDir/index_meta.json` (internal/indexer/indexer.go:107-114). Schema version sentinel is Bleve internal key `_swartznet_schema_version` holding an ASCII integer, outside the document store; a mismatch on open triggers a full clean rebuild (indexer.go:18-24,134-154).
- Schema v3, one index, two doc types discriminated by field `type` (default `torrent`). Torrent docs: `infohash` (keyword), `name` (standard analyzer), `files` (standard; all paths joined with `\n` into one string), `trackers` (keyword array), `size_bytes` (numeric), `added_at` (RFC3339 datetime), `file_count` (numeric), `signed_by` (keyword, lowercased hex; added in v3). Content docs: `infohash`, `file_index`, `file_path` (keyword), `file_size`, `mime`, `text` (standard analyzer — the searchable body), `extractor`, `indexed_at`. Full-text fields carry Store+Index+IncludeInAll+IncludeTermVectors (internal/indexer/schema.go).
- Doc ID scheme: torrent = `t:` + lowercase infohash; content = `c:` + lowercase infohash + `:` + fileIndex + `:` + chunkIndex — re-index is put-or-replace, chunks independent (indexer.go:188-190; content.go:39-41).
- Chunking constants: target chunk 2048 bytes, max overrun ratio 1.5, small-file factor 1.25 (files ≤ 2560 B stay one chunk), 64 MiB text output cap and 64 MiB per-archive-entry decompression bound (internal/indexer/chunker.go).

**Command outputs and inputs outside the share root**

- `swartznet create -o <path>` writes a standard metainfo file (CreatedBy default "SwartzNet", single-tier AnnounceList, optional top-level `snet.pubkey`/`snet.sig`), mode 0644, atomic (internal/engine/create.go:120-185).
- `swartznet aggregate build --out <path>` writes the signed Aggregate B-tree payload (format in §3.2), mode 0644, after reading JSONL records (`{"kw":string,"ih":40-hex,"t":int64 optional}` per line) from `--in` or stdin; `kw` must be non-empty and `ih` must hex-decode to 20 bytes (cmd/swartznet/cmd_aggregate_build.go:22-27,180-236).
- `add` and `gui --torrent` read caller-supplied `.torrent` files; `aggregate inspect`/`find` read a caller-supplied index file.
- Logs go to stderr only; the node writes no log files.

### 3.2 Wire formats (BitTorrent extensions, LTEP messages, DHT items, HTTP API shapes — names + shapes + where defined)

The compatibility constraint governs everything here: a vanilla client observes only BEP-3/5/9/10/44 traffic; `sn_search` frames are sent only to peers that advertised the extension, and all SwartzNet DHT data rides standard BEP-44 mutable items.

**LTEP / `sn_search` extension** (spec: docs/06-bep-sn_search-draft.md; code: internal/swarmsearch/wire.go, sync_wire.go)

- Frame envelope: standard BEP-10 — uint32 big-endian length, uint8 msg id 20, uint8 ext msg id (0 = LTEP handshake, else receiver-assigned ID for `sn_search` from the handshake `m` dict), followed by one bencoded dict.
- Every `sn_search` payload is a single bencoded dict with integer discriminator `msg_type`: 0=query, 1=result, 2=reject, 3=peer_announce, 4=sync_begin, 5=sync_symbols, 6=sync_need, 7=sync_records, 8=sync_end (wire.go:13-18; sync_wire.go:19-25).
- `Query` (0): `{txid uint32, q string, scope subset of "n"/"f"/"c" (default "nfc"), limit, lang, min_size, max_size, not_ih [][]20-byte}` (wire.go:36-46).
- `Result` (1): `{txid echo, total, partial, hits[]}`; `Hit` = `{ih 20B, ih2 32B opt, n name, s seeders, l, sz size, t unix, rank 0-1000, matches[]}`; `FileMatch` = `{fi file index, fp path, pr, sn snippet, off offset}` (wire.go:49-108).
- `Reject` (2): `{txid, code 0-4, reason}`.
- `PeerAnnounce` (3): `{v int, services uint64, pk 32B optional (present iff Publisher bit set), endorsed [][]byte max 10×32B}` (wire.go:209-226).
- `ServiceBits` uint64, append-only: bit 0 ShareLocal, 1 ShareSwarm, 2 FileHits, 3 ContentHits, 4 LayerDPublisher, 5 CompanionPublisher, 6 CompanionSubscriber, 7 SnippetHighlight, 8 Regtest, 9 SetReconciliation; bits 10-63 reserved; unknown bits ignored (internal/swarmsearch/services.go:18-77).
- Sync frames (4-8), RIBLT set reconciliation: `SyncBegin` `{txid, algo "riblt-v1", filter{pubkeys required, since?, prefix?}, element_size must = 32, local_count, max_symbols, max_bytes}`; `SyncSymbols` `{txid, symbols[{c int32, h uint64, b 32B}] ≤100 per message, done, index = position of first symbol}`; `SyncNeed` `{txid, ids[] 32B ≤1000, empty = done}`; `SyncRecords` `{txid, records[{pk 32B, kw, ih 20B, t, pow, sig 64B}] ≤500, missing[]}`; `SyncEnd` `{txid, status converged|limit_exceeded|aborted, decoded, sent, bytes_in, bytes_out, abort_code}`. Budget defaults: 2000 max symbols, 1 MiB max bytes; record wire-size proxy = 32+len(kw)+20+8+8+64 bytes (sync_wire.go:34-140; sync_session.go:540-542).
- Signed keyword record (`LocalRecord`): `{Pk[32], Kw ≤64B, Ih[20], T int64, Pow uint64, Sig[64]}`; signature message = `pk || kw || ih || LE64(t) || uvarint(pow)` (identical to companion.RecordSigMessage). RIBLT element ID = `SHA-256(pk || kw || ih || t_littleEndian)` — deliberately excludes pow and sig so re-signed records dedupe (sync_session.go:522-559; record_cache.go:226-235).
- RIBLT internals: coded symbol `{Count int32 signed, KeyXOR uint64, DataXOR [32]byte}`; element key = FNV-1a-64 of the 32-byte ID; membership `contributes(key, idx)` = `SplitMix64(key + idx*0x9E3779B97F4A7C15) % 2^(1+idx%12) == 0` — a 12-step geometric rate cycle (internal/swarmsearch/riblt.go:36-90).

**DHT items (BEP-44/46/51)** (spec: docs/07-bep-draft, docs/05 §PPMI; code: internal/dhtindex)

- BEP-44 canonical signing buffer for all mutable puts: the literal byte string `4:salt<len>:<salt>3:seqi<seq>e1:v<len>:<v>`; target = SHA1(pubkey || salt) (docs/07:219-227).
- `KeywordValue` (Layer D): bencoded `{ts int64, hits:[{ih 20B, n? name, s? seeders, f? files, sz? size}], more? int (reserved), next_pk? 32B (reserved, never populated in v1)}`, total ≤1000 bytes (the BEP-44 `v` cap); salt = lowercased UTF-8 keyword ≤64 bytes; shard salts `keyword#N` (internal/dhtindex/schema.go:32-103).
- BEP-46 companion pointer: mutable item at salt `_sn_content_index`, value `{ih 20B, ts int64 omitempty}`; ts=0 decodes as "unknown freshness, accept" (internal/dhtindex/dht.go:183-198; internal/companion/publisher.go:23).
- PPMI (Publisher Pointer Mutable Item, v0.5): fixed 32-byte salt = `SHA256("snet.index")`; value `{ih 20B (aggregate index torrent), commit? 32B (= Trailer.TreeFingerprint), topics? 32B cuckoo digest, ts int64, next_pk? 32B reserved for key rotation}`, ≤1000 bytes; seq is the native BEP-44 monotonic counter (internal/dhtindex/ppmi.go:52-86).
- Publish discipline: ≤5 puts/sec, hourly refresh cycle, success requires ≥1 confirmed storing node. All inbound DHT values (keyword values, pointers, PPMIs) are size-capped before decode.
- BEP-51 `sample_infohashes` is used outbound for indexer discovery and by `crawl-probe`; the probe's JSON output shape is `{addr, target(40hex), samples[]40hex, interval int64, num int64, nodes[]"<40hex-id>@<addr>"}` (cmd/swartznet/cmd_crawl_probe.go:98-125).

**Signed `.torrent` format** (spec: docs/11-signing-protocol.md; code: internal/signing/signing.go:45,205-210)

- Two optional top-level bencode keys outside the info dict (so the infohash is unchanged): `snet.pubkey` (exactly 32 bytes) and `snet.sig` (exactly 64 bytes).
- Signature payload = 14-byte literal `"SN-TORRENT-V1|"` || 20-byte SHA-1 infohash = always 34 bytes.
- One key without the other = treat as unsigned (logged, no hard error); re-signing overwrites; verifiers must tolerate unknown `snet.*` keys; future versions bump the domain-separation prefix.

**Companion content index (torrent payload)** (internal/companion/types.go:48-121, serialize.go:19-78)

- Single gzip stream containing JSON `CompanionIndex`: `{version:1, format:"swartznet-content-index", publisher: hex64?, generated_at: unix, torrents:[{infohash hex40, name, size?, added_at?, files:[{index, path, size?, mime?, extractor?, chunks:[{text, offset?}]}]}]}`; format-magic and version guarded on decode.
- Wrapped in a v1 single-file torrent, piece length 256 KiB, empty announce list, file name `swartznet-content-index-<first-12-hex-of-pubkey>-v1.json.gz` (internal/companion/torrent.go:19,85-109).
- Consumers cap untrusted inputs: 32 MiB metadata cap, 1 GiB decompressed-JSON cap.

**Aggregate B-tree index (SNAGG, torrent payload)** (normative spec docs/research/SPEC.md §1-3; code: internal/companion/btree.go)

- One page per BitTorrent piece; piece size 16 KiB–4 MiB (MinPieceSize 16384). 16-byte page header: magic `"SNAGG\0"` + version 0x01 + kind (0x00 root / 0x01 interior / 0x02 leaf / 0xFF trailer) + level + flags + LE16 payload-length + 4 reserved-zero bytes (btree.go:25-72).
- Record (bencoded): `{pk 32B, kw string ≤64B, ih 20B, t int64, pow uvarint hashcash nonce, sig 64B}`; encoded size ≤256 bytes by construction; sort/lookup key = `kw || 0x00 || ih`; sig message = `Pk || Kw || Ih || LE64(T) || uvarint(Pow)` (btree.go:76-196).
- Leaf payload = LE16 count + repeated (uvarint length + bencoded Record); interior payload = LE16 count + repeated (uvarint separator-length + separator + LE32 child-piece-index), first separator forced empty. Root is always piece 0 (btree.go:252-432).
- Trailer (always the last piece), 162-byte little-endian payload: trailer_version(1)=0x01, pubkey(32), seq(8), created_ts(8), root_piece_index(4)=0 invariant, num_pages(4), num_records(8), min_pow_bits(1), tree_fingerprint(32) = SHA256 of the concatenated canonical sorted record encodings, publisher_sig(64) ed25519 over all preceding fields (btree.go:59-72,438-564). Hashcash PoW difficulty D=20 on records in the published spec; `aggregate build --pow-bits` refuses values >40.

**HTTP API** (internal/httpapi/server.go:307-346 for the mux; default bind `localhost:7654`, empty `--api-addr` disables the API entirely)

- Global behavior: 1 MiB request-body cap; CSRF/DNS-rebinding guard on state-mutating methods (Origin/Referer host and Host header must be loopback, fails closed); server timeouts ReadHeader 2s / Read 5s / Write 30s / Idle 60s; loud warning when bound non-loopback (the API is unauthenticated); unconfigured collaborators return 503 "not configured"; mutation responses share the envelope `{ok:true, infohash, ...}` (server.go:807-816,1190-1194; bodylimit.go:12; csrf.go:25-53).
- `POST /search` — request `{q (required, ≤1024 bytes), limit (default 50, cap 500), swarm bool, dht bool, swarm_timeout_ms (default 2000, cap 30000), dht_timeout_ms (default 5000, cap 30000), signed_by hex64, highlight bool}`. Response is the layer-reconciliation seam: `{local: always present {total, hits:[] never null}, swarm?: present only when requested and wired, dht?: likewise}`. Per-layer hit shapes are never merged: LocalHit `{doc_type, infohash, name, size_bytes, file_index, file_path, mime, extractor, score, signed_by, fragments map[string][]string}`; SwarmHit `{infohash, name, size, seeders, score, sources}`; DHTHit `{infohash, name, seeders, size, files, sources}`; swarm/dht sections carry `{asked, responded, rejected, hits, error?}` / `{indexers_asked, indexers_responded, hits, error?}` (server.go:396-493; docs/05-integration-design.md:117).
- `GET /healthz` → `{ok, version}`; version is a process-global atomic, shared by every Server instance (server.go:1235-1253).
- `GET /status` → `{local:{indexed, doc_count}, swarm:{known_peers, capable_peers}, publisher:{pubkey?, total_keywords, total_hits, keywords:[{keyword, hits_count, publish_count, last_published, last_error}]}, dht?:{good_nodes, nodes}, bloom?:{bit_size, hash_functions, population_bits, estimated_items}, reputation?:{known_indexers, top_indexers[≤10]{pubkey, score, hits_returned, hits_confirmed, hits_flagged}}}` — dht/bloom/reputation are omitempty pointers so absent subsystems disappear rather than render zeros (server.go:615-688).
- `POST /confirm` `{infohash hex40}` → `{ok, infohash}` (503 when no bloom filter); `POST /flag` `{infohash}` → `{ok, infohash, indexers_flagged}` — demotes only source-attributed indexers, fails closed to 0.
- `POST /torrent` `{uri magnet}` → `{ok, infohash}`.
- `GET`/`POST /capabilities` — one body shape for both: `{share_local 0-2, file_hits 0-1, content_hits 0-1, publisher 0-1}`; POST clamps values and echoes the result (server.go:929-937).
- `GET /torrents` → `{torrents:[{infohash, name, size, bytes_completed, bytes_missing, progress 0..1, files, active_peers, half_open_peers, pending_peers, total_peers, seeders, paused, status (metadata|downloading|seeding|paused|queued), indexing, indexed_files?, index_extracted?, queued, download_rate, upload_rate, signed_by?, trusted_publisher?}]}` — a JSON-tagged mirror of engine.TorrentSnapshot re-declared in httpapi so httpapi never imports internal/engine (server.go:68-106).
- `POST /torrents/{infohash}/pause` | `/resume`, `DELETE /torrents/{infohash}` → `{ok, infohash, action}` (infohash must be 40 hex); `POST /torrents/{infohash}/indexing` `{enabled bool}` → `{ok, infohash, enabled}`; `GET /torrents/{infohash}/files` → `{infohash, files:[{index, path, display_path, length, bytes_completed, progress, priority none|normal|high}]}`; `POST /torrents/{infohash}/files/{index}/priority` `{priority}` → `{ok, infohash, index, priority}`.
- `GET /aggregate` → `{ppmi_enabled, known_indexers, indexers:[{pk, label?}], record_source_kind?, record_cache_size?, record_cache_max?, services, bootstrap?:{anchors, admitted, pending}}`; `services` is a fixed-width 16-char lowercase big-endian hex rendering of the 64-bit ServiceBits, no `0x` prefix (internal/httpapi/aggregate.go:25-156). (This endpoint exists in code but is absent from all shipped docs.)
- `GET /companion` → `{publisher:{last_refresh, last_infohash, last_error?, published_count, pubkey_hex?}, subscriber:[{pubkey_hex, label?, last_sync_at?, last_error?, torrents_imported, content_imported, generated_at?, pointer_infohash?}]}`; time fields serialize RFC3339 and the zero value `0001-01-01T00:00:00Z` is the web UI's "never" sentinel. `POST /companion/refresh` → `{ok}` (429 when throttled); `POST /companion/follow` `{pubkey hex64, label?}` and `/unfollow` `{pubkey}` → `{ok}` (internal/httpapi/companion.go:41-155).
- `GET /index/stats` → `{dir_bytes, doc_count, torrent_count, content_count, corpus_text_bytes, inflation_ratio}` (server.go:690-700).
- `GET`/`POST /config/rate-limit` `{upload_bps, download_bps}` (0 = unlimited, POST echoes); `GET`/`POST /config/queue` `{max_active_downloads}`.
- `GET /{$}` and `GET /static/` serve the embedded web UI (index.html, app.js, style.css compiled in via go:embed; internal/httpapi/web/embed.go:17-18).

**HTTPS anchor bootstrap** (internal/daemon/bootstrap_https.go:79-85)

- Last-resort GET of a well-known JSON endpoint returning `{"version":int, "anchors":["<64-char hex pubkey>"], "comment":string omitempty}` — pubkeys only, never records; future fields must be optional for old-client compatibility.

**Environment variables**

- `XDG_DATA_HOME` — relocates the entire share root; `HOME` is the fallback (config.go:442-449).
- `SWARTZNET_LOG` = `debug|info|warn|error` — slog level for both binaries (cmd/swartznet/main.go:142; cmd/swartznet-gui/main.go:149).

## 4. External dependencies and integrations

### 4.1 Wire-compatibility constraint (governs every dependency choice)

- The load-bearing constraint is mainline compatibility: a vanilla BitTorrent client observing a SwartzNet node must see nothing but BEP-3/5/9/10/44 traffic — no new reserved bit (BEP-4 registry deliberately unused), no new DHT verb, no new UDP port. All SwartzNet-specific traffic rides inside BEP-10 LTEP extension messages and BEP-44 mutable DHT items (docs/06-bep-sn_search-draft.md; docs/05-integration-design.md §8).
- The `sn_search` LTEP extension name uses the `sn_` prefix specifically to avoid colliding with libtorrent's `lt_` extension namespace (internal/swarmsearch/protocol.go:13-15).
- Any change to handshakes, LTEP messages, or DHT items must keep the vanilla-client interop matrix in docs/05-integration-design.md §8 green; a pinned vanilla anacrolix client (v1.61.0, built in a temp module) serves as the independent interop peer in testbed scenario s11 (testbed/).

SIGCOMM 2024 (graduated-degree cycle `mod=2^(1+idx%12)`, FNV-1a keys), not the cited yangl1996/riblt library (internal/swarmsearch/riblt.go:1-24; MILESTONE-v0.5.0.md:42-47). `internal/swarmsearch` deliberately avoids importing the torrent package proper (interface seam `LtepAdvertiser`, internal/swarmsearch/protocol.go:455-462) and duplicates record shapes rather than importing `internal/companion`/`internal/indexer` (internal/swarmsearch/sync_wire.go:106-118).
- **Borrowed designs (patterns, not code):** Bitcoin Core AddrMan tried/new tables (internal/swarmsearch/peerbook.go:8-38), `Misbehaving()` with DISCOURAGEMENT_THRESHOLD=100 and 24h bans (internal/swarmsearch/misbehavior.go:8-84), feeler connections (internal/swarmsearch/feeler.go:8-16), BIP-9-style services bits with unknown-bit tolerance (internal/swarmsearch/services.go:3-17), BIP-152 compact-relay concept for the hit cache (internal/swarmsearch/hitcache.go:7-21); EigenTrust-style seed anchors for reputation cold start.

### 4.3 The MPL-2.0 boundary discipline

- `anacrolix/torrent` and `anacrolix/dht/v2` are MPL-2.0, which is file-level copyleft. The discipline that shapes the whole integration architecture: never patch or vendor-modify library files — use only public extension APIs (callbacks, LTEP user-protocol registration, direct DHT server access). All first-party files remain Apache-2.0 (LICENSE at repo root) (CLAUDE.md; docs/05-integration-design.md:162-179).
- THIRD_PARTY_LICENSES at the repo root is the curated redistribution notice file (explicitly "not a full SBOM"; defers to `go mod graph`, go-licenses, cyclonedx-gomod for completeness, THIRD_PARTY_LICENSES:143-145). Known gaps as of the "As of v0.3.0" pin: klauspost/compress and the entire Fyne/systray/go-gl stack linked into the GUI binary.

### 4.4 Protocols by BEP number

- **BEP-3** — core metainfo/peer protocol, byte-for-byte mainline. Signing relies on vanilla clients ignoring unknown top-level metainfo keys (`snet.pubkey`, `snet.sig`); qBittorrent/Transmission/libtorrent interop claimed (internal/signing).
- **BEP-4** — reserved-bit registry; deliberately NOT used (LTEP chosen instead so vanilla peers see nothing new).
- **BEP-5** — DHT/KRPC; bootstrap and peer discovery.
- **BEP-9** — `ut_metadata`/magnet; also the architectural template for the `sn_search` extension; `x.pe=` peer hints used in testbed magnets.
- **BEP-10** — LTEP; the sole peer-wire extension point, carrying all `sn_search` traffic (query/hits, sync frames, `peer_announce`).
- **BEP-11** — `ut_pex`; supported via the engine; design model for search-peer gossip.
- **BEP-19** — HTTP web seeds (engine support; surfaced in GUI copy).
- **BEP-27** — private flag (`create --private`).
- **BEP-42** — DHT node-ID-from-IP security; obeyed by default, disabled only via `--dht-insecure` for private testbed DHTs.
- **BEP-43** — read-only DHT flag; honored.
- **BEP-44** — mutable DHT items; Layer-D storage point. Hard limits a rebuild must respect: 1000-byte value cap, 64-byte salt cap, ~2h storage TTL (hence 1h re-announce cadence), monotonic `seq`; target = SHA1(pubkey ‖ salt), giving each publisher its own keyword namespace.
- **BEP-46** — mutable-pointer pattern; companion-index pointer under salt `"_sn_content_index"` (a second salt convention, SHA256("snet.index"), exists on the PPMI path — see §7).
- **BEP-51** — `sample_infohashes`; used by `crawl-probe` and planned bootstrap channel B; cited precedent for negotiation-free DHT queries.
- **BEP-52** — v2 fields `ih2`/`pieces_root` recognized in metainfo; a per-file `pr` hit field is reserved for future use.
- **Study-only references (no wire impact):** BEP-14 (LSD), BEP-18, BEP-49 (chunking-scheme study) (docs/04-bep-extension-points.md).

### 4.5 External services and network endpoints

- **DHT bootstrap nodes:** with `DHTBootstrapAddrs` empty, the node uses anacrolix's default public bootstrap routers (router.bittorrent.com et al.); a non-empty list fully replaces the defaults — used by the testbed to build private DHTs (internal/config/config.go:88-92; internal/engine/engine.go:587-600).
- **Trackers:** none by default. `create` accepts caller-supplied tracker URLs as a single announce tier; trackerless torrents are valid and expected (DHT-first design) (internal/engine/create.go:36).
- **HTTPS anchor fallback:** a last-ditch bootstrap path fetching `{"anchors": ["<64-hex ed25519 pubkey>", ...]}` from an operator-supplied URL. `https://` scheme is enforced (plaintext could inject anchor pubkeys); default client timeout 15s; idempotent re-anchor with dedupe. No URL is hardcoded and nothing invokes it automatically today (internal/daemon/bootstrap_https.go:31,81,99,146).
- **No other external services.** No telemetry, no central search server. The HTTP API binds loopback only (default port 7654), relies on OS trust rather than auth tokens, and defends against browser-origin attacks with an in-package CSRF/DNS-rebinding guard (internal/httpapi/csrf.go:10-38).

## 5. Non-obvious rules and edge cases (a rebuild MUST preserve these)

### 5.1 Wire compatibility and the `sn_search` protocol

- Mainline compatibility is the load-bearing constraint: no new reserved handshake bit, no new DHT verb, no new UDP port, no second overlay. Every extension rides the BEP-10 LTEP `m` dictionary, plain BEP-44 items, or ordinary torrents; capability is announced only via the `m` dict. Whole design families (BitSwap, GossipSub, iroh-blobs, HyParView, relays, publish-along-path, Autobase, and all Bitcoin chain/consensus machinery) were rejected on this ground alone — "take the peer layer, leave the chain" (docs/05-integration-design.md:663-665,804-812; docs/04-bep-extension-points.md:56-64; docs/research/A-content-routing.md:41-122; docs/10-bitcoin-lessons.md:24-54).
- Threat-model partition is explicit: spam, poisoning, sybil, and tamper resistance are in scope; anonymity, query privacy, censorship resistance, and content policy are out of scope (bring your own VPN/Tor) (docs/05-integration-design.md:679-694).
- **[weird]** The extension name is `sn_search` with prefix `sn_`, never `lt_` — `lt_` is historically libtorrent's namespace, and doc 04's worked examples all say `lt_search` but its closing section overrides the name; only the closing section is normative (docs/04-bep-extension-points.md:1218-1223; docs/06-bep-sn_search-draft.md:95).
- Never send an `sn_search` frame to a peer that did not advertise `sn_search` back; vanilla peers must only ever see an unknown name in the LTEP `m` dict, and unknown extended message IDs are dropped silently with no error signalled (internal/swarmsearch/doc.go:23-26; protocol.go:509-527; docs/04-bep-extension-points.md:205-210,1127-1138).
- **[weird]** Extended message IDs are per-direction and per-peer: each side picks arbitrary numeric IDs for extensions it is willing to receive, and the sender must use the receiver's advertised number — the two directions normally use different numbers for the same extension (docs/04-bep-extension-points.md:196-200,753-761).
- Inner message-type numbering is frozen: 0=query, 1=result, 2=reject, 3=peer_announce, 4-8=sync. txid echo is mandatory; result/reject frames from peers outside a query's fan-out set are dropped and charged as misbehavior (docs/04-bep-extension-points.md:250-256; docs/06-bep-sn_search-draft.md:158-171,189-192).
- ServiceBits numbering is append-only; unknown bits MUST be ignored, never rejected — this is the additive-forever forward-compat contract. Absence of peer_announce means services 0, NOT a protocol error, and a responder must not refuse a query solely because the initiator never announced (internal/swarmsearch/services.go:11-21,74-77; docs/06-bep-sn_search-draft.md:128-138,278-283).
- **[weird]** Announced services = `ServicesFromCapabilities(caps)` OR (`DefaultServices()` minus BitLayerDPublisher), with the publisher bit re-added only when `caps.Publisher>0` — so default bits (including BitShareLocal) are always advertised even after the operator downgrades capabilities via POST /capabilities; only the Publisher bit actually tracks runtime caps (internal/swarmsearch/protocol.go:547-556).
- **[weird]** The publisher pubkey is gossiped in peer_announce only when `caps.Publisher>0` AND a 32-byte key is set, and the engine flips Publisher=1 only when neither `--no-dht-publish` nor `--no-index` is set. Passive nodes must never gossip themselves as indexers; the gossip path gates on `caps.Publisher>0`, not pubkey presence (a past bug: pubkey set but Publisher=0 made gossip silently never fire). Gossip-learned pubkeys are labelled `gossip:<peer_addr>` (internal/swarmsearch/protocol.go:552-564; internal/engine/engine.go:996-1004,1077-1098; internal/notes/overnight-progress.md:150-156).
- An all-zero 32-byte pubkey in peer_announce is rejected (impossible ed25519 identity; accepting it would poison the indexer fan-out set on every reconnect) while the rest of the frame is still processed (internal/swarmsearch/handler.go:132-150; CHANGELOG.md:1131-1142).
- **[weird]** Endorsements count only when the endorsing peer announced its own pubkey in the same frame; self-endorsements and all-zero candidates are skipped. The endorsed-list cap of 10 is enforced asymmetrically — encode errors out, decode silently truncates and drops wrong-length entries without failing the frame ("local validation fault, not a protocol violation") (internal/swarmsearch/handler.go:167-186; wire.go:226-269).
- **[weird]** Bit 8 (BitRegtest) is deliberately a "loud" capability so accidental regtest→mainnet cross-connections are obvious in peer state (docs/06-bep-sn_search-draft.md:124).
- txid match alone never authenticates a response: the sender must be in the query's immutable asked-set (populated before registerPending); results/rejects from unasked peers are charged as spoofing, and malformed results are charged BEFORE the pending lookup so guessing a live txid cannot dodge the charge (internal/swarmsearch/query.go:84-97,176-190,287-312).
- A Result is "semantically malformed" iff Total>0 with zero hits OR any hit infohash is not exactly 20 bytes; within one peer's Result, duplicate infohashes are deduplicated so a responder cannot double-count Rank toward the 1000 cap or pad Sources with its own address (internal/swarmsearch/query.go:437-467).
- **[weird]** Merge semantics look ad hoc but are contract: score = sum of ranks capped at 1000; name = first non-empty; size = first non-zero; seeders = max; matches = concatenated union; sort by score desc with seeders-desc tiebreak; rejects are delivered to the collector as a Result with MsgType=MsgTypeReject (internal/swarmsearch/query.go:341-349,469-501).
- Responder ranking is spec'd: 0.4·bm25(name) + 0.2·bm25(files) + 0.2·bm25(content) + 0.1·log(seeders+1) + 0.1·freshness where freshness = exp(−(now−t)/30d), ×1000 rounded to int 0-1000; queriers are free to re-rank the merged union (docs/05-integration-design.md:522-535).
- Fan-out selection: all tried peers plus up to FeelerCount(2) new peers; fall back to ALL supported peers when there is no book, the tried table is empty (bootstrap), or the tried set has zero overlap with currently-connected supported peers (internal/swarmsearch/query.go:363-429).
- **[weird]** Feeler probes reuse the real Query path with the magic query string `__sn_feeler__` (syntactically valid, unlikely to match) so promotion happens through the identical code path as user queries; remote nodes run a genuine local search for it (internal/swarmsearch/feeler.go:22-99).
- **[weird]** PeerBook promotion happens only on observed behavior (a valid Result), never on advertised capability; AddNew never demotes a tried entry; timeouts and rejects both count as Failures but v1 never auto-demotes. OnPeerClosed drops peer state, rate-limit bucket, and PeerBook entries, so promotion is per-connection-lifetime only — this looks like lost state but is intentional v1 scope (internal/swarmsearch/peerbook.go:98-172; query.go:241-259; protocol.go:619-638).
- Ban/misbehavior state is strictly local and NEVER gossiped (shared bans are an eclipse-attack vector — the Bitcoin banman lesson); bans survive OnPeerClosed (Forget keeps banned entries) but not restart; expired bans auto-clear with a fresh score budget (internal/swarmsearch/misbehavior.go:22-24,136-186; docs/10-bitcoin-lessons.md:246-252).
- The per-peer rate-limit token bucket starts FULL (burst 10) on first query; zero QueriesPerSecond or Burst disables limiting entirely; config changes keep existing buckets, which refill at the new rate (internal/swarmsearch/ratelimit.go:66-112).
- **[weird]** ShareLocal==1 ("answer only for current-swarm torrents") is deliberately treated the same as ShareLocal==0 and rejected with code 4: no swarm-aware searcher exists, and serving the full index under it would silently violate the operator's intent — fail closed rather than over-serve (internal/swarmsearch/handler.go:678-690).
- Empty scope means "responder's choice" and is always accepted; unknown scope letters are ignored for forward compatibility; only explicit 'c'/'f' requests against a node lacking those capabilities are rejected (never silently downgraded — wire-compat matrix row 8.4-B) (internal/swarmsearch/handler.go:694-701,835-852).
- **[weird]** Sync frames (msg_types 4-8) are gated on the REMOTE peer having announced BitSetReconciliation (bit 9); violations get reject code 2 — a deliberately reused code ("unsupported scope"), not a new one — plus a misbehavior charge (internal/swarmsearch/handler.go:232-242; services.go:66-72; docs/research/SPEC.md:238-240).
- **[weird]** `sync_symbols.index` MUST equal the receiver's running symbols-in count; any mismatch (dropped/reordered frame) is a hard session abort, because encoder/decoder positions desync permanently and reconciliation would silently produce wrong differences (internal/swarmsearch/sync_session.go:276-286).
- **[weird]** Sync budgets negotiate downward only: ApplyBegin takes min(peer's max_symbols/max_bytes, own defaults 2000 symbols / 1 MiB); crossing the symbol budget maps to sync_end "limit_exceeded", other violations to "aborted". Byte accounting uses the semantic record size (32+kw+20+8+8+64), not actual bencoded bytes (internal/swarmsearch/sync_session.go:214-220,436-475,540-542).
- **[weird]** Responder sessions cap at 4 per peer, where a re-begin on an existing txid replaces rather than counts; sessions older than 2 min are reaped lazily on the next inbound sync frame from that peer (no background goroutine), each emitting sync_end "aborted"; a zero-record responder answers sync_begin with an immediate sync_end "converged" — valid wire behavior for non-publishers (internal/swarmsearch/handler.go:211-222,298-366,578-619).
- ApplyRecords is phase-gated: sync_records is only legal after this side sent sync_need (PhaseNeeded) or during a streaming fulfilment (PhaseFulfilled); records straight after sync_begin are a violation (internal/swarmsearch/sync_session.go:442-449).
- **[weird]** The RIBLT element key MUST be a nonlinear function of the ID bytes (FNV-1a-64): a linear key would make XOR-composed symbols self-consistent for phantom elements and the decoder would hallucinate decodings. The `contributes()` 12-step modulus cycle {2..4096} is what guarantees pure symbols emerge for any difference size in [2,4096] — both are cross-implementation wire-compat requirements (internal/swarmsearch/riblt.go:40-53,71-90).
- **[weird]** Record ID = SHA-256 over pk||kw||ih||t_LE, deliberately EXCLUDING pow and sig (two valid signings of the same semantic record must share one ID or global reconciliation never converges); the derivation is intentionally duplicated in sync_session.go and record_cache.go and must stay byte-identical to both and to SPEC §2.4 (internal/swarmsearch/sync_session.go:544-559; record_cache.go:220-235; docs/research/SPEC.md:292-302).
- **[weird]** Signature verification of synced records happens in swarmsearch (charge 20 on failure), but PoW threshold enforcement is deliberately NOT there — it belongs to the RecordSink, and there is intentionally no ScoreInsufficientPoW constant (internal/swarmsearch/misbehavior.go:64-71; handler.go:457-469).
- Sync rate limits are local config knobs, not wire constraints: 1 active sync session per TCP connection, 1 initiation per peer per 5 min, 10 MB of sync_records per peer per hour (docs/research/SPEC.md:400-411).
- **[weird]** The "capable subset" of search-aware peers is a VIEW over the full DHT routing table, never a separate routing table — polluting the routing table with capable-only entries is explicitly forbidden; capable peers are pre-seeded from BEP-10 sessions that advertised the extension (docs/04-bep-extension-points.md:1050-1063,1144-1146).
- Any node holding index data must obey BEP-42 (node ID derived from IP via crc32c) and BEP-43 (honor `ro:1`, don't table read-only nodes), or modern clients evict it from routing tables and the index becomes unreachable (docs/04-bep-extension-points.md:407-437,1093-1096).
- Search-hit record shapes should keep room for an optional BEP-52 per-file merkle root (`pr`) alongside `ih` so future versions can deduplicate the same file across repackaged torrents (docs/04-bep-extension-points.md:680-687,1254-1258).

### 5.2 DHT keyword index (Layer D) and BEP-44

- **[weird]** The anacrolix BEP-44 wrapper must have `ServerConfig.Exp` pinned to 2h: upstream `NewAnacrolixDhtServer` leaves Exp=0, which makes every stored mutable item instantly expired — put succeeds, get returns "value not found". Dropping this pin silently breaks all of Layer D; it is pinned by TestLayerDDHTClusterRoundTrip and testbed s12 (internal/engine/engine.go:616-635; CHANGELOG.md:627-647; internal/testlab/layerd_dht_cluster_test.go:8-22).
- **[weird]** A put whose traversal reached zero DHT nodes is a FAILURE even though `getput.Put` returns nil error in that case — otherwise MarkPublished advances and the 55-min throttle suppresses retries for an item nobody can fetch. One shared `checkPutStats` guard covers all three put paths (keyword, BEP-46 pointer, PPMI) so the check cannot drift (internal/dhtindex/dht.go:41-53,286-295; ppmi_dht.go:77-82).
- Publisher throttles: MinPutInterval 55 min per keyword (just under the 1h refresh and 2h BEP-44 TTL; anacrolix has no put rate cap of its own, so this is the self-DoS guard — 0 disables it for tests/regtest); design budget 5 puts/sec total; 3 consecutive failures mark a keyword unhealthy with daily retry; only items with activity in the last 24h are refreshed. Every put uses getput's discovered seq+1, clamping at MaxInt64 instead of wrapping (internal/dhtindex/publisher.go:36-53,244-261; dht.go:20-35; docs/05-integration-design.md:299-304,622-629).
- **[weird]** Layer D publishes ONLY `Tokenize(torrent.Name)` keywords — never content tokens. A rewrite that publishes or queries content words gets permanent zero hits (testbed s12 queries "corpus" from the torrent name, while Layer-L/S scenarios query a content marker) (CHANGELOG.md:910-914; testbed/scenarios/s12-swarm-dht.sh:86-94).
- Tokenization is a cross-implementation contract: lowercase Unicode letters, digits pass through unchanged, split on everything else, drop tokens <3 bytes, drop file-extension noise (mp4/iso/pdf/...), drop stopwords (deliberately short, English-only list — "a missed stopword is one extra DHT put; a dropped legitimate keyword is permanently un-discoverable"), dedup preserving first-appearance order, cap 8 keywords applied AFTER filtering; the searcher picks the longest non-stopword token (internal/dhtindex/tokenize.go:24-124; docs/07-bep-dht-keyword-index-draft.md:147-165,240-247).
- Keywords whose UTF-8 salt exceeds 64 bytes are DROPPED, never truncated — truncation could alias distinct keywords onto one DHT target (internal/dhtindex/schema.go:11-15,154-164).
- **[weird]** EstimateValueSize stamps a representative non-zero Ts before marshalling because EncodeValue overwrites Ts=0 with a 10-digit timestamp at put time; estimating with Ts=0 would let a near-cap entry pass eviction but fail the live encode, making the keyword permanently unpublishable (internal/dhtindex/schema.go:127-149).
- Manifest.AddHit evicts the OLDEST hit (slice front) while the encoded value exceeds 1000 bytes; replacing an existing hit can still trigger eviction (the replacement may be larger); multi-shard spill is deliberately NOT the v1 overflow mechanism. Keyword entries that become empty are deleted so refreshAll never re-publishes empty values; RemoveTorrent → publisher.Retract scrubs the infohash from every keyword (internal/dhtindex/manifest.go:137-222; schema.go:43-53; CHANGELOG.md:424-435).
- Shard-overflow salt convention (reserved, not used by v1 overflow): shard 0 at the bare keyword, overflow shards at `keyword#1`, `keyword#2`, ...; readers fetch the root first then fan out (docs/07-bep-dht-keyword-index-draft.md:132-144).
- **[weird]** Lookup.Query issues a DHT get for ONLY the first token of the query (multi-keyword AND/OR is deferred); an empty indexer set or a reputation-filtered-to-empty set returns an empty response, not an error. Multi-word search is single-keyword lookup plus client-side intersection — AND/OR must never be pushed into the DHT (internal/dhtindex/lookup.go:257-313; docs/03-p2p-search-protocols.md:996-999).
- Layer-D hit score = mean(source reputations; 0.5 when no tracker) + 0.05 per extra source capped at +0.2 + 0.25 flat Bloom boost, clamped [0,1]; sort order is BloomHit desc, score desc, source count desc, name asc; source label falls back to the first 16 hex chars of the pubkey (internal/dhtindex/lookup.go:419-422,471-528).
- Publishers whose PPMI resolves are excluded from the legacy per-keyword fan-out (no double-query), but IndexersAsked counts the combined set; PPMI fetch failure silently falls back to legacy (internal/dhtindex/lookup.go:315-340).
- BEP-46 pointer `ts` is omitempty on the wire; decoders treat absent/zero ts as "unknown freshness, accept" for back-compat with pre-ts publishers (internal/dhtindex/dht.go:108-126,183-186).
- All remote-value decoders (keyword, pointer, PPMI) reject payloads over the 1000-byte BEP-44 cap BEFORE unmarshalling — a malicious node can return up to ~64 KiB regardless of the storage cap (internal/dhtindex/schema.go:105-125; ppmi.go:123-135; dht.go:219-240).
- **[weird]** The BEP-51 crawler forwards pubkeys with INVALID signatures to the sink (sigValid=false) so reputation/admission can demote them; unsigned torrents (the vast majority) are silently skipped; only malformed bencode is an error — forwarding known-bad signatures looks wrong but feeds the demotion pipeline (internal/dhtindex/crawler_publisher.go:29-58; crawler_tick.go:95-110).
- **[weird]** Two salt-derivation conventions coexist: the companion pointer uses the literal ASCII salt `_sn_content_index` while PPMI uses SHA256("snet.index") — the PPMI double-hash is deliberate so passive DHT observers can't classify publishers by salt; the pointer salt simply predates that decision and must not be "fixed" (internal/companion/publisher.go:18-23; internal/dhtindex/ppmi.go:8-40).
- **[weird]** KeywordValue keeps `next_pk` on every wire message but v1 NEVER populates it — the wire shape is frozen now so subscribers can adopt key rotation later without a format bump; `ih2` was removed from v1 for the opposite reason (unpopulated bytes against the 1000-byte cap). Rotation is deliberately not linkable for legacy items (old entries expire in 2h; clean-slate reputation is a feature); next_pk rides the current key's signature so only the current holder can announce a successor (docs/07-bep-dht-keyword-index-draft.md:196-214,375-382).
- BEP-44 mechanics that must be preserved exactly: bencoded v ≤ 1000 bytes (error 205), salt ≤ 64 bytes (207), strictly monotonic seq with no-downgrade semantics (302), ed25519 signature over the literal buffer `4:salt<len>:<salt>3:seqi<seq>e1:v<len>:<v>` (206), CAS field for racing publishers (301), get-before-put write tokens, ~1h republish against ~2h expiry. BEP-44 has no append primitive, so "add an infohash to a keyword" is a CAS-guarded read-modify-write, and multi-publisher aggregation is a client-side union over trusted pubkeys, not a protocol feature (docs/04-bep-extension-points.md:449-565,874-990).
- Layer-D privacy contract: the keyword crosses the wire only as a SHA1 target (dictionary attack possible, accepted); planned SOCKS5 proxying is scoped to the BEP-44 put path ONLY, never swarm traffic; Tor/I2P daemon integration explicitly rejected (docs/05-integration-design.md:323,358-362; docs/09-v1-blocker-research.md:363-366).
- Legacy per-keyword BEP-44 read compatibility must be retained ≥12 months after the Aggregate migration; old items are left to expire via TTL, never actively deleted (docs/research/SPEC.md:562-563).

### 5.3 Companion and aggregate index torrents

- The companion file basename embeds the first 12 hex chars of the publisher pubkey (empty pubkey falls back to the legacy generic name); subscribers locate the payload by the path returned from FetchCompanionTorrent, never by filename — the tagged name is cosmetic (internal/companion/types.go:8-35; torrent.go:27-35; CHANGELOG.md:500-503).
- The companion infohash intentionally changes on every refresh (Encode embeds a fresh GeneratedAt); the publisher overwrites both files in place and treats CompanionDir as exclusive (internal/companion/torrent.go:40-45).
- **[weird]** An empty local index is recorded as a refresh FAILURE ("nothing to publish"); `lastAttempt` advances on any outcome (throttles RefreshNow) but `lastRefresh` advances ONLY on success — it answers "is my pointer still alive (<2h BEP-44 TTL)?" and must never be advanced by a failure (internal/companion/publisher.go:125-139,305-365).
- Companion seeding errors from AddTorrentMetaInfo are swallowed (debug log only) because re-adding the same infohash is benign — anacrolix dedupes internally (internal/companion/publisher.go:324-329).
- Companion fetch fails closed BEFORE requesting any piece: exactly 1 file, declared length ≤ 32 MiB (the info dict is attacker-controlled via the pointer), plain filename only (rejects '', '.', '..', '/' and '\' — backslash included so a manifest written on another OS can't smuggle a separator past Windows); the returned path is hand-built as DataDir/<info.Name>; ctx cancel aborts the wait but leaves the torrent in the engine for retry reuse (internal/engine/engine.go:85-94,1285-1375).
- Decode enforces a 1 GiB decompressed-JSON cap and requires the exact Format string and Version==1; Encode force-overwrites Format/Version and normalises nil Torrents to [] so the wire form is stable (internal/companion/serialize.go:19-78).
- **[weird]** Subscriber ingest: infohash is lowercased and must be exactly 40 chars or the record is skipped; FileCount is recomputed as the count of non-empty file paths, not the publisher's claimed count; empty-text chunks are skipped but ChunkIndex still reflects their original position; the first hard index error aborts the whole ingest (internal/companion/subscriber.go:249-308).
- A sync result arriving for a publisher unfollowed mid-sync is dropped (membership re-checked under the lock) so results never resurrect for unfollowed keys (internal/companion/subscriber.go:491-499).
- **[weird]** B-tree interior-page separators are NOT classic between-children separators: each child's stored separator is the MIN KEY of that child's own subtree, the first child's separator is forced empty (= −∞) at encode time, and a child's upper bound is the NEXT child's separator — a rewrite using textbook separators would mis-route queries (internal/companion/btree.go:269-283; read_btree.go:270-284).
- **[weird]** B-tree reader trust model: only the trailer and per-record signatures are signed; interior pages are attacker-controlled. The walk therefore uses one shared visited-set failing closed on ANY page revisit (defeats Fibonacci-growth fan-in), requires child indices strictly increasing, strictly greater than the parent, and below the trailer piece, and requires ≥3 pages, root at piece 0, and trailer NumPages == actual piece count — capping the walk at NumPieces fetches (internal/companion/read_btree.go:66-92,175-294; CHANGELOG.md:78-86).
- **[weird]** Find silently DROPS records failing signature or PoW verification instead of erroring the query — once the trailer verified there is nothing a subscriber can do about individual bad records; PoW is enforced only when trailer MinPoWBits>0 (0 = v1.0 back-compat/test mode), and BuildBTree deliberately does NOT default MinPoWBits so unit tests don't mine (internal/companion/read_btree.go:98-168; build_btree.go:129-132).
- **[weird]** BuildBTree output must be byte-deterministic: records are defensively copied then sorted by RecordKey; the fingerprint is SHA256 over the concatenated canonical record encodings in sorted order, independent of piece size, so two publishers with identical records produce identical files, infohashes, and PPMI commits — this is what makes RIBLT convergence coherent across the network. A single-leaf tree still gets a distinct one-child root page (root kind ≠ leaf kind) (internal/companion/build_btree.go:8-11,122-166,215-230; docs/research/SPEC.md:32-35,216-218).
- PoW mine-then-sign ordering is mandatory (RecordSigMessage includes the PoW nonce); MineRecordPoW refuses bits>40 as cost-prohibitive; VerifyFingerprint bails as soon as record count exceeds the trailer claim so a crafted file can't force unbounded hashing (internal/companion/pow.go:33-45; read_btree.go:330-339).
- **[weird]** Hashcash is minted at D=0 during the dual-read migration window even though MinPoWBitsDefault=20; readers enforce the trailer's min_pow_bits, so raising D is a coordinated schema bump, not a flag flip (docs/research/MILESTONE-v0.5.0.md:238-240; internal/companion/btree.go:45-48).
- Load-bearing constants: PieceSize ∈ [16384, 4 MiB]; MaxKeywordBytes=64; MaxRecordBytes=256; page payload lengths uint16; MinPoWBitsDefault=20; companion torrent piece length 256 KiB; publisher queue size 64, drop-on-full. `aggregate inspect|find --piece-size` defaults to 16384 and MUST match the wrapping torrent's metainfo piece length or B-tree paging is misread (internal/companion/build_btree.go:44-50; btree.go:48-57; torrent.go:19; cmd/swartznet/cmd_aggregate.go:69-71,116-118).

### 5.4 Engine behavior (anacrolix integration)

- **[weird]** Rate limiters must have a positive burst even in unlimited mode (unlimitedBurst = math.MaxInt32): anacrolix's openNewConns refuses to dial when `DownloadRateLimiter.Tokens() <= 0`, so a zero burst silently blocks ALL outgoing connections. Nonzero limits set burst to one second of tokens with a 16 KiB floor (the largest single anacrolix reservation is a 16 KiB chunk) (internal/engine/ratelimit.go:9-16,58-85; engine.go:642-650).
- **[weird]** The DHT server MUST be given a PeerStore, or get_peers replies carry no write token and vanilla clients' announce_peer stalls (a BEP-5 break); the same shared InMemory instance also backs the local per-infohash peer table (internal/engine/engine.go:574-586).
- **[weird]** Inbound `sn_search` frames MUST be handled asynchronously: anacrolix holds the client lock during PeerConnReadExtensionMessage, so a synchronous reply self-deadlocks and a synchronous Bleve search stalls every peer. The payload must be copied because the decoder buffer is reused. Admission is bounded by two 256-slot semaphores (handlers and reply writers) with drop-on-full, never queue (internal/engine/engine.go:716-794,72-83; swarmadapter.go:25-41).
- **[weird]** Download activation sets priority per-file instead of Torrent.DownloadAll: anacrolix keeps two parallel priority surfaces, and DownloadAll leaves File.Priority stuck at "none" in snapshots (internal/engine/engine.go:1901-1918; queue.go:140-155).
- **[weird]** The magnet→metainfo session-upgrade goroutine must never run for file/metainfo-added entries: a re-marshalled metainfo can differ byte-wise from the original and metainfo.Load rejects it with "expected EOF" on restore; the guard checks both TorrentFile presence and AddedVia (internal/engine/engine.go:1648-1695; CHANGELOG.md:1192-1207).
- **[weird]** Seed-from storage keys file paths on the real on-disk basename (ContentName, custom FilePathMaker), NOT info.Name, so a torrent created with a renamed display name still seeds in place while downloaders see the chosen name; the basename persists as session field `content_name` with legacy fallback to info.Name. Piece completion for such storage is kept in memory deliberately — never drop a completion DB into the user's source directory — and VerifyData on create/restore repopulates it (internal/engine/engine.go:1429-1451; session.go:64-73; CHANGELOG.md:40-51).
- **[weird]** Every add path (create, restore, metainfo) kicks a background VerifyData rehash because anacrolix verifies lazily on peer request — without it a fresh seed or restored torrent shows 0% forever when no peer asks (internal/engine/engine.go:1488-1506,1869-1877; CHANGELOG.md:545-562).
- **[weird]** A torrent with per-torrent indexing disabled still submits its name keywords to the DHT publisher and still mints aggregate records — the opt-out only skips the local Bleve write and content extraction ("publish a torrent's existence without exposing its file list in local searches") (internal/engine/engine.go:2067-2097).
- **[weird]** The BEP-46 pointerPutter is built even in leech-only/NoIndex mode — companion pointer publication is its own opt-in via CompanionDir, independent of the keyword publisher (which IS suppressed by DisableDHTPublish/NoIndex); the lookup path always stays alive (internal/engine/engine.go:995-1098).
- Queue semantics: queued torrents keep metadata fetch and indexing (only the file-priority flip is deferred); metadata-only torrents count as active downloads; seeding (complete) torrents never occupy a slot; reducing the cap does NOT demote already-active torrents. The count-then-activate decision is serialized on a dedicated promoteMu (separate from e.mu) so N concurrent autoDownload goroutines from a batch restore can't over-subscribe (internal/engine/queue.go:23-49,64-127,101-106,161-166).
- Paused state is applied at registration time, before any background goroutine spawns, so a restored-paused torrent can never race into Normal priority; activateDownload refuses paused handles; ResumeTorrent re-runs queueOrActivate to flip priorities that were never set (internal/engine/engine.go:1548-1553,1835-1850; queue.go:96-100,140-145).
- Restore rejects session TorrentFile values that aren't plain basenames, so a hand-edited/corrupted manifest cannot read outside the torrents dir (internal/engine/engine.go:1767-1776).
- **[weird]** persistAdd only overwrites MagnetURI/TorrentFile when non-empty, specifically so an upgradeMagnetSession that raced ahead doesn't get clobbered with empty strings (internal/engine/engine.go:1601-1614).
- **[weird]** fileTracker fans out to N subscribers with per-subscriber drop-on-full, and keeps a 64-slot doneReplay buffer so late subscribers still receive events for files already complete at startup (replay overflow drops with a warning) — the earlier single-shared-channel design silently split events between CLI progress and the indexer. `Handle.FileEvents()` creates a NEW subscription per call, so evaluating it inside a for/select loop hangs forever; callers must bind once (SubscribeFileEvents is the explicit alias) (internal/engine/file_tracker.go:24-55,81-111; engine.go:520-539; CHANGELOG.md:836-853,1144-1164).
- Rate sampling: the first snapshotOf call returns 0 rates; calls <100 ms apart return the cached previous rate (designed for the GUI's 2-second poll) (internal/engine/engine.go:440-482).
- **[weird]** snapshotOf must not touch Length/BytesMissing/Stats/Files before Info() is non-nil — anacrolix v1.61.0 nil-panics pre-metadata; only InfoHash/Name/IsPaused are safe (internal/engine/engine.go:2259-2295).
- Background waiter timeouts are load-bearing: autoDownload/autoIndex give up after 5 min without metadata, upgradeMagnetSession/verifyOnRestore after 10 min, autoConfirmOnComplete after 24 h; all also unblock on bgCtx cancel, and autoConfirm additionally on the per-handle removed channel (internal/engine/engine.go:1673-1680,1888-1928,1949-1967).
- Duplicate adds (same infohash) return the existing Handle rather than erroring, mirroring anacrolix's own dedupe (internal/engine/engine.go:1554-1560).
- Close order matters: cancel bgCtx, stop the indexing pipeline before storage shuts down, stop the publisher before the DHT server dies, save bloom/reputation, close subscriptions, then client.Close. engine.New never fails over a corrupt session/bloom/reputation/trust/identity — all degrade to warnings (internal/engine/engine.go:2494-2538,882-977).
- **[weird]** AddTorrentMetaInfo returns `any` instead of *Handle deliberately, so internal/companion can consume it without importing internal/engine (internal/engine/engine.go:1388-1393).
- **[weird]** `x.pe=` magnet peer hints must be dotted-quad IP:port, never hostnames — anacrolix feeds the raw string into its peer list as StringAddr with lazy resolution and silently drops non-dotted-quad hints (this is why the testbed pins static IPAM subnets) (CHANGELOG.md:1016-1048; testbed/docker-compose.swarm.yml:34-43).

### 5.5 Indexing and extraction (Layer L)

- **[weird]** Extractor dispatch is first-claim-wins in registration order, and registration order is Go init() order = alphabetical by filename within the package. plaintext.go therefore registers BEFORE subtitle.go and must explicitly DECLINE subtitle MIME types (application/x-subrip, text/vtt, text/x-ssa) so SubtitleExtractor can claim them — changing file names or registration order silently changes which extractor handles a format (internal/indexer/extractors/extractor.go:90-101; plaintext.go:114-143).
- **[weird]** Raw .html/.htm files are indexed by the PLAINTEXT extractor with tags left in (text/html is in plaintext's accept list); the tag-stripping HTML walker is used only for XHTML inside EPUBs and ZIM articles — there is no standalone HTML extractor (plaintext.go:133; htmltext.go:16-18).
- **[weird]** Extract errors count as "skipped", not "failed": only OpenReader failure or all-chunks-write-failure increments failed; extract error/timeout/panic logs at Debug as pipeline.extract_skip; the invariant Processed == Extracted+Skipped+Failed always holds (internal/indexer/pipeline.go:156-237).
- **[weird]** The extract watchdog (60s, a var so tests can shrink it) deliberately LEAKS the wedged extractor goroutine — Go can't kill goroutines — and the file reader is closed only inside the extracting goroutine after Extract returns, never by the caller, because anacrolix torrent.Reader Read/Close race is unsafe (internal/indexer/pipeline.go:271-334).
- Schema mismatch (including a missing/corrupt sentinel, which reads as version 0) triggers os.RemoveAll of the ENTIRE index directory and silent recreation — no migration path; torrent docs regenerate via autoIndex on restore, but content docs only repopulate when file-complete events re-fire (internal/indexer/indexer.go:46-105,134-147; CHANGELOG.md:1298-1300).
- **[weird]** Torrent file paths are flattened into one '\n'-joined string for the `files` field and split back on '\n' when reconstructing TorrentDoc — a path containing a newline would corrupt round-tripping (internal/indexer/indexer.go:195-213,541-543).
- Layered extraction caps are contract: dispatch-time size ceilings (subtitle 16 MiB; rtf/fb2 50 MiB; mobi 64 MiB; plaintext/exif 100 MiB; id3/archive 500 MiB; flac/ogg 1 GiB; mkv/mp4 64 GiB); input read caps of 256 MiB via LimitReader for pdf/docx/odt/odp/pptx/epub; per-zip-entry DECOMPRESSED stream cap maxDocTextBytes=64 MiB (deflate amplifies ~1032:1 — without it one text node OOMs inside Token()/Next() where recover() cannot catch); output accumulation caps truncate gracefully (index partial text) rather than error; the engine sets the pipeline's global per-file cap to 100 MiB via SetIndex (internal/indexer/extractors/extractor.go:42-52; docx.go:78-82; epub.go:91-99; archive.go:46-51; internal/engine/engine.go:313-325).
- **[weird]** Content-chunk target is 2 KiB — M13e shrank it from 10 KiB based on BM25-relevance research, so a rewrite copying the design doc's "~10KB chunks" would regress relevance. Split preference is paragraph (blank line, tolerating \r\n) → line → hard split at target; a paragraph up to 1.5× target stays whole; text ≤1.25× target returns as a single chunk at Offset 0; flushed chunks carry byte offsets into the source text (internal/indexer/chunker.go:19-118; CHANGELOG.md:2062-2068).
- Query limits: MaxSearchLimit=10000 is defence-in-depth inside Index.Search, above the httpapi cap of 500 and the sn_search cap of 100; Limit≤0 defaults to 20; the only rejected request shape is empty Query AND empty SignedBy (internal/indexer/indexer.go:26-32,696-712).
- SignedBy filtering and content-for-infohash selection use exact-match TermQuery (never QueryString) so a hostile infohash/pubkey cannot inject Bleve query grammar; both values are lowercased before matching (internal/indexer/indexer.go:722-729,820-831; content.go:94-98).
- All paginated index walks run 1000-doc pages under the single global mutex with a defensive ceiling of (count/batch)+2 pages, logging a *_truncated warning if hit; deleteByQueryLocked instead FAILS CLOSED with an error after (initialTotal/batch)*2+4 iterations if deletes are ineffective (internal/indexer/indexer.go:333-371,440-528,846-887).
- **[weird]** EPUB chapter order is deliberately wrong-for-humans: the OPF spine is ignored and .xhtml/.html/.htm entries are concatenated in lexical filename order — order is irrelevant to a keyword index and this avoids an OPF parser (internal/indexer/extractors/epub.go:18-23,75-88).
- The archive extractor indexes member NAMES only (never contents), sorted, capped at 4 MiB of concatenated names, with the tar.gz decompression walk bounded at 1 GiB; format is detected by magic bytes (PK\x03\x04 / gzip 1f8b / tar-by-trial), not extension (internal/indexer/extractors/archive.go:15-51,60-104).
- Plaintext rejects files with a NUL byte in the first 4 KiB, strips a UTF-8 BOM, and returns invalid-UTF-8 files anyway with bad bytes replaced by U+FFFD ("searching the readable parts beats failing") (internal/indexer/extractors/plaintext.go:44-88).
- **[weird]** MIME resolution consults SwartzNet's extTypes override map BEFORE stdlib mime.TypeByExtension — Go's builtin table lacks .txt, so Alpine/scratch deployments silently skip plaintext extraction without the override, and `.ts` means TypeScript, not MPEG-TS; stdlib results have any `;charset=` suffix stripped (internal/indexer/extractors/extractor.go:132-164; CHANGELOG.md:855-866).
- **[weird]** ZIM cluster decompression uses a true-LRU 32-entry cache specifically because the URL pointer list is only roughly cluster-sorted and random eviction thrashes; XZ-compressed (type 4) clusters are skipped by design, so pre-2021 ZIMs index zero articles (internal/indexer/extractors/zim.go:39-44,94-102).
- IndexContent rejects empty Text with an error, while extractors signal "no text" with a nil chunk slice + nil error; the pipeline drops zero-chunk results as "skipped" before any index write (internal/indexer/content.go:64-70; pipeline.go:195-198).
- **[weird]** Local and remote (companion-subscribed) documents share one index and one doc-ID namespace — a remote publisher's record for infohash X occupies the same `t:x`/`c:x:i:c` IDs as a local add, so whichever writes last wins; remote torrent docs carry no Trackers/SignedBy (internal/companion/subscriber.go:269-305; internal/indexer/indexer.go:188-190).
- Fragments maps are deep-copied from Bleve and only populated when Highlight was requested; highlighting is scoped to fields name/files/text only, using Bleve's HTML style (`<mark>`) (internal/indexer/indexer.go:740-747,808-814).
- Bleve Store=true on the text field is a deliberate v1 tradeoff (snippet highlighting over 3-5× disk) (docs/09-v1-blocker-research.md:53-73).
- Backpressure drops, never blocks: the file-complete→extract channel has capacity 64; a full channel drops the request and an hourly background scan picks up missed files (docs/05-integration-design.md:596; CHANGELOG.md:329-352).
- **[weird]** `indexed_files` counts all processed files (extracted + skipped + failed) — binary files producing zero chunks still increment it; `index_extracted` counts the text-yielding subset (internal/notes/overnight-progress.md:233-259).

### 5.6 Identity, signing, trust, and reputation

- **[weird]** identity.key file permissions must be EXACTLY 0600 — anything else, including the stricter 0400, is rejected as "compromised" with an instruction to chmod or delete; comparison is against the literal perm bits, deliberately ignoring umask (internal/identity/identity.go:18,69-75).
- On load, the public half (bytes [32:64]) is re-derived from the 32-byte seed and compared, so independent corruption fails loud at load time instead of surfacing later as "signature does not verify" (internal/identity/identity.go:89-96).
- Auto-creation of a missing identity is allowed ONLY at the default XDG path; any explicitly user-supplied --identity/--key path is load-only and fails closed (a typo would silently sever publisher reputation by signing under a fresh key). Identity is never regenerated implicitly; --identity without --sign is a usage error (cmd/swartznet/cmd_create.go:64-98; cmd_aggregate_build.go:110-146). Ephemeral publisher keys are rejected by design; the long-term rotation plan is the reserved next_pk PPMI field (docs/09-v1-blocker-research.md:353-375).
- The signature payload is exactly 34 bytes: the 14-byte literal `SN-TORRENT-V1|` (trailing pipe is decorative but byte-exact) followed by the raw 20-byte infohash; the domain prefix is the version anchor — v2 means a new prefix plus new field names, never in-band negotiation (internal/signing/signing.go:45,201-210; docs/11-signing-protocol.md:100-124,386-394).
- SignBytes decodes the metainfo as map[string]bencode.Bytes so the info-dict bytes pass through untouched (infohash preserved); the re-encode canonicalizes top-level key order but never alters info. A rewrite that round-trips info through a typed struct would change the infohash and break everything (internal/signing/signing.go:90-118).
- **[weird]** snet.pubkey/snet.sig must remain TOP-LEVEL metainfo fields, outside the info dict — the signature binds the infohash, so they cannot live inside info without recursion, and signed/unsigned twins must share one infohash/swarm ("moving them inside would fork the network"). This deliberately trades away BEP-9 crawlability: magnet adds always get signed_by="" because BEP-9 only transports the info dict (docs/11-signing-protocol.md:66-77; docs/research/MILESTONE-v0.5.0.md:205-229; docs/05-integration-design.md:149).
- **[weird]** Verification error taxonomy: missing snet fields → ErrNotSigned (a normal outcome); wrong pubkey/sig lengths → a plain error (neither sentinel); crypto failure → ErrBadSignature with the Signature struct still fully populated. UIs MUST distinguish ErrNotSigned (benign) from ErrBadSignature (firm tamper signal) and SHOULD NOT penalise unsigned torrents in default rankings (internal/signing/signing.go:156-184; docs/11-signing-protocol.md:210-215,404-413).
- **[weird]** A .torrent with a BAD signature is still added and downloads normally — the engine only warns and leaves SignedBy empty; verification only happens on the file-add path (internal/engine/engine.go:1199-1231).
- Trust pubkeys are normalized to lowercase at every boundary; invalid-hex entries are silently dropped on load; Add on an existing key overwrites the label; List/save order is sorted by pubkey (internal/trust/trust.go:81-108,143-157).
- Reputation score formula (constants are ranking-compat contract): neutral 0.5 for zero-counter records; otherwise (max(0, confirmed−flagged)/max(1, returned)) Bayesian-smoothed toward 0.5 with prior weight 5; plus seed bonus 0.45·2^(−age/90d) if SeededAt is set (negative age clamped to 0); final clamp [0,1]. The 90-day half-life means organic reputation dominates after one quarter (fresh seed ≈ 0.95); puzzle/WoT bootstrap was explicitly rejected (internal/reputation/reputation.go:74-91,239-279; docs/09-v1-blocker-research.md:229-241).
- Tracker.Threshold treats cutoff ≤ 0 or NaN as "always passes" — MinIndexerScore=0 (the default) disables filtering entirely; snapshot ordering is score-desc with pubkey-asc tiebreak (internal/reputation/reputation.go:294-318).
- **[weird]** Re-importing an already-seeded pubkey (seed-list reload or anchor re-admit) refreshes SeededAt to now, restarting the bonus decay — "maintainers re-bless the list" is intentional, not double-counting (internal/reputation/reputation.go:322-331).
- **[weird]** Bloom filter index derivation is frozen by the on-disk format: h1 = FNV-64a(input); h2 = the SAME hash state continued with one extra 0xff byte, then h2 |= 1 (forced odd stride, Kirsch-Mitzenmacher); index_i = (h1 + i·h2) mod m. Reproduce this exactly or existing known-good.bloom files return garbage membership (internal/reputation/bloom.go:204-220).
- Bloom defaults: 1,000,000 expected items at 0.01 FP rate (≈9.6M bits ≈1.2MB); m/k from the standard formulas with ceil and floor-at-1; the loader rejects m==0, k==0, and any bitsLen ≠ (m+63)/64 — both undersized AND oversized — to fail closed on corrupt files (internal/reputation/bloom.go:38-43,228-279).
- **[weird]** Flagging fails closed: with no SourceTracker attribution for the infohash, NO reputations are demoted (HTTP, GUI, everywhere) — the earlier fallback of demoting every known indexer was removed as attacker-weaponizable (seed one unattributed spam hit → one flag craters the whole table). After a successful flag the SourceTracker entry is Forgotten so repeated flags cannot double-dock the same indexers; the HTTP endpoint returns ok:true even when zero indexers were flagged (internal/httpapi/server.go:855-888; internal/gui/search.go:446-458; internal/reputation/sources.go:107-150).
- **[weird]** Trusted-publisher torrents are auto-confirmed into the known-good Bloom the moment metadata arrives (autoIndex time), not at download completion — the trust relationship substitutes for the completion signal; untrusted torrents only reach the Bloom via completion or explicit confirm (internal/engine/engine.go:2099-2114,1941-1986).
- **[weird]** The Bloom filter and reputation tracker are persisted ONLY at engine Close, while trust.json is saved on every mutation — a crash loses the session's confirmations/flags/auto-confirms by design (internal/engine/engine.go:2516-2527; internal/trust/trust.go:99-118).
- RecordReturned ignores n ≤ 0, and indexers whose fetch errored are not counted at all — reputation only accrues on responses that actually carried hits, so silent non-responders neither gain nor lose (internal/reputation/reputation.go:166-175; internal/dhtindex/lookup.go:411-418).
- CLI split: `swartznet trust *` operates directly on trust.json offline (no daemon); `flag`/`confirm` require a running daemon via localhost HTTP (default localhost:7654) (cmd/swartznet/cmd_trust.go:14-17; cmd_flag.go:37-96).

### 5.7 Publisher bootstrap and admission

- Anchor admissions are exempt from the MaxTrackedPublishers cap (default 100; the cap check is len(admitted)−anchorsAdmitted ≥ cap); anchors get reputation MarkSeeded — NOT RecordReturned(pk,0), which is a silent no-op — while bep51/endorsement candidates start at the unknown score 0.5 and must earn reputation. Default EndorsementThreshold is 3 strong endorsers (tracker reputation ≥ 0.5 each; without a tracker ANY endorser counts) (internal/daemon/bootstrap.go:66-72,401-484; CHANGELOG.md:614-625).
- **[weird]** bloomPolicy default-denies when no Bloom filter is attached (keeps the crawl channel quiet on a cold cache) and otherwise admits on tracker score ≥ 0.3 — the Bloom filter's CONTENTS are never consulted; presence alone gates, and since unknown pubkeys score 0.5, an unknown crawl candidate passes whenever a bloom + tracker are attached. Candidates that fail the gate are retained in the "observed" set so IsPending stays truthful and later endorsements can promote them (internal/daemon/bootstrap.go:300-319,434-458).
- **[weird]** runAnchorLoop skips the initial anchor-fetch run when zero anchors are configured (the dev default) and instead waits on `anchorsAdded` — a buffered size-1 coalescing signal fired by the HTTPS fallback only when it added >0 new anchors; without this, a late HTTPS-supplied anchor list would never be fetched (internal/daemon/bootstrap.go:94-98,226-238; bootstrap_https.go:207-217).
- The HTTPS bootstrap fallback is https-scheme-only at the public entry point (a loopback-http exemption exists solely for tests), response body hard-capped at 64 KiB (read cap+1 to detect overflow), non-200 rejected, malformed hex anchors skipped silently — and the endpoint serves only PUBKEYS, never records, so compromising it can only delay bootstrap, not poison the index (internal/daemon/bootstrap_https.go:38-50,74,119-206; docs/research/SPEC.md:538-546).
- **[weird]** Follow-file loading has asymmetric failure: a file >1 MiB fails closed wholesale (half-loading would silently drop a suffix of the user's follows), but individually malformed pubkey rows are skipped with a stderr warning and the rest load; a missing file is success (0, nil). Errors are BOTH written human-readably to stderr and returned for the structured logger — the dual reporting is intentional back-compat (internal/daemon/follows.go:30-91; daemon.go:163-173).
- CandidateFromCrawl requires sigValid=true (valid snet.sig before admission); callers verify ed25519 upstream, and the swarmsearch observer adapter hardcodes true because sync records were already per-record verified (internal/daemon/bootstrap.go:300-304; daemon.go:54-65).

### 5.8 Configuration, paths, and environment gates

- Startup/teardown order is load-bearing and fixed: engine → indexer → companion publisher → companion subscriber → bootstrap → session restore → HTTP API; Close must first cancel+join the daemon-owned background goroutines before any subsystem teardown, so no anchor fetch touches the engine during Close even if the caller never cancels the parent ctx (internal/daemon/daemon.go:100-108,260-287).
- Options.NoIndex must be mirrored into Cfg.NoIndex before engine construction — skipping only Bleve while leaving Cfg.NoIndex false would keep the Layer-D keyword publisher announcing under the user's identity, a documented privacy regression. `add --no-index` does not set cfg itself; the daemon copies the flag down so Config.NoIndex and Options.NoIndex stay dual representations of one setting (internal/daemon/daemon.go:90-98; cmd/swartznet/cmd_add.go:33,99).
- Empty string = feature off, consistently: IndexDir="" (index validation skipped), CompanionDir="" (companion pub+sub disabled), CompanionFollowFile="" (in-memory follows only), TrustPath="" (trust nobody automatically), APIAddr="" (no HTTP API), ListenPort=0 (OS-assigned). Frontend --port flags use sentinel −1 for "keep config default" precisely so 0 stays meaningful; only port ≥ 0 overrides (internal/config/config.go:200-225,265-270; cmd/swartznet/cmd_add.go:40,82-84; cmd/swartznet-gui/main.go:57,92-94).
- **[weird]** TWO distinct env-var gates guard the same dangerous flags, from two independent review findings: the CLI refuses --regtest/--dht-insecure without SWARTZNET_UNSAFE=1 (exit 2; flags omitted from usage text), and config.Validate independently rejects Regtest/DHTInsecure unless testing.Testing() is true OR SWARTZNET_ALLOW_REGTEST=1. A production binary needs BOTH; each gate's error message names only its OWN env var; both match the exact string "1" ("yes"/"true" do not unlock) (cmd/swartznet/cmd_add.go:59-73; internal/config/config.go:23,277-300).
- **[weird]** Production package internal/config imports "testing" — it looks like a mistake but is the deliberate test-binary detection mechanism: any `go test` binary bypasses the config-layer gate via testing.Testing(), which is how testlab sets Regtest=true with no env vars; the boolean is threaded into dangerousFlagsRejected(inTest) as a parameter so the production branch stays unit-testable (internal/config/config.go:15,277-300; internal/testlab/cluster.go:152).
- **[weird]** Validate creates DataDir itself but only IndexDir's PARENT — Bleve must create the leaf directory (Bleve errors if the leaf pre-exists as an empty dir). These MkdirAll side effects run BEFORE the dangerous-flags rejection, so even a refused regtest config creates DataDir on disk (internal/config/config.go:262-279).
- Regtest accelerations are exact contract constants, same code paths as production (no mocks): dhtindex Publisher RefreshInterval 1h→5s, MinPutInterval 55m→100ms; companion Publisher Interval 1h→10s, MinInterval 1m→100ms; the engine logs `engine.regtest_mode_active` at Warn (internal/config/config.go:125-152; internal/daemon/daemon.go:134-137).
- GUI-persisted config is deliberately restricted to DataDir/IndexDir (the "torrents on a separate disk" preference); port/DHT knobs are excluded on purpose — which also keeps Regtest/DHTInsecure out of GUI reach. Precedence: Default() < saved config.json < CLI flags; empty fields are omitted from the JSON so the next launch falls back to Default() rather than locking in blank strings (internal/config/config.go:375-413; cmd/swartznet-gui/main.go:67-96).
- **[weird]** ListenHost exists specifically because BEP-44 write tokens are keyed on the query's source IP and OS source-IP flapping on a 0.0.0.0 bind silently rejects puts; DisableIPv6 exists because dual-stack spawns two DHT servers, the Publisher drives only one, and v4-mapped-v6 addresses break put round-trips. Both default off (internal/config/config.go:38-50,97-108).
- RestoreSession's error is deliberately discarded — per-entry failures are warn-logged in the engine and must never block daemon startup; likewise httpapi Start failure leaves d.API nil rather than failing New (internal/daemon/daemon.go:223-228,250-254).
- The httpapi package must never import internal/engine or internal/companion; the daemon translates snapshots field-by-field through adapters. Layer isolation is architectural law: three response types (indexer.SearchResponse / swarmsearch.QueryResponse / dhtindex.LookupResponse) reconciled only at the httpapi boundary, no shared cross-layer type (internal/daemon/adapters.go:17-25,90-120; docs/05-integration-design.md:117).
- SWARTZNET_LOG's level switch has no "info" case — "info", empty, and unknown values all fall through to LevelInfo; the function is duplicated verbatim in the CLI and GUI mains and the copies must stay behavior-identical (cmd/swartznet/main.go:140-151; cmd/swartznet-gui/main.go:147-158).

### 5.9 HTTP API and web UI contracts

- Layer failure asymmetry: a Layer-L (local Bleve) error fails the whole POST /search with 500, but Layer-S and Layer-D errors are swallowed into a 200 response as `swarm.error`/`dht.error` strings — the CLI and web UI header rendering depend on this shape (internal/httpapi/server.go:531-534,565-567,592-594; web/static/app.js:199,204).
- The swarm/dht response sections appear ONLY when the request asked for that layer AND the collaborator is wired; asking for swarm on a swarm-less daemon silently omits the section rather than erroring. `local.hits` is initialized to an empty slice so it serializes as [] never null (internal/httpapi/server.go:521,555,586).
- **[weird]** Per-layer timeout budget: the client's ms value is clamped to (0, 30s], defaults 2s (swarm) / 5s (DHT), and the handler context gets timeout+500ms — the extra 500ms grace lets the fan-out layer return partial results before the HTTP context dies; 30s deliberately mirrors the server WriteTimeout. The CLI's API request deadline is swarmTimeoutMs + dhtTimeoutMs + 2000 ms (internal/httpapi/server.go:129-151,556-557,587-588; cmd/swartznet/cmd_search.go:109-110).
- Magic limits clients depend on: search limit default 50 / cap 500; query cap 1024 bytes; request body cap 1 MiB; reputation top_indexers truncated to 10; header cap 256 KiB; the web UI separately caps its limit input at 100 (internal/httpapi/server.go:127,158,512-519,777-780; bodylimit.go:12; web/index.html:38).
- CSRF guard checks Origin first and consults Referer only when Origin is absent; the literal hostname "localhost" is trusted but any other DNS name is rejected even if it resolves to 127.0.0.1 (DNS-rebinding defense); GET/HEAD/OPTIONS are always exempt. Middleware nesting is withMaxBodyBytes(withCSRFGuard(mux)), so a CSRF-rejected request never reads its body — swapping the order changes DoS characteristics (internal/httpapi/csrf.go:41-69,91-107; server.go:352-357).
- **[weird]** POST /capabilities and POST /config/* have replace semantics, not merge: SetCapabilities overwrites the entire struct and POST /config/rate-limit always writes both fields, with zero meaning "unlimited" rather than "unchanged". Clamp ranges: share_local 0..2; file_hits/content_hits/publisher 0..1 (internal/httpapi/server.go:1096-1134,1207-1222).
- Every /torrents/{infohash} route validates an exactly-40-char lowercase-hex-decodable path segment before touching the engine (400 otherwise); the file index uses strconv.Atoi specifically because Sscanf would silently accept "3abc" (internal/httpapi/server.go:1059-1070,1179-1183).
- **[weird]** Companion refresh maps ANY RefreshNow error to HTTP 429 — the expected error is the publisher's MinInterval throttle and the GUI shows the message verbatim; follow/unfollow errors map to 500, pubkey parse errors to 400 (must be exactly 64 hex chars, length-checked before hex-decode) (internal/httpapi/companion.go:94-105,118-169).
- API routes are registered before the static-file catch-all; the root handler pattern `GET /{$}` matches only the exact root, so unknown paths 404 out of the file server — deliberately no SPA-style index.html fallback (internal/httpapi/server.go:335-343).
- **[weird]** The web UI injects Bleve highlighter fragments and highlighted names via innerHTML, on the explicit assumption that Bleve's HTML highlighter pre-escapes text and only adds `<mark>` tags — a rewrite of either side that drops that escaping guarantee becomes an XSS (web/static/app.js:271-304).
- **[weird]** Web UI back-compat: /index/stats, /torrents, and /aggregate fetches in the Status tab must tolerate 404 from older daemons via `.catch(()=>null)` — enforced by a test that greps the embedded JS source for the literal pattern (web/static/app.js:412-417; web/aggregate_card_test.go:64-72).
- Poll cadences are part of the UX contract: health 5s always; downloads 2s and status 4s only while their tab is visible (re-armed via setTimeout, cancelled when hidden); control actions trigger an immediate refresh (web/static/app.js:150,423-427,606-609,770-772).
- **[weird]** The web UI derives its status pills from torrent.status string values 'downloading'/'seeding'/'queued'/'paused' and defaults to 'metadata' — the engine's status vocabulary is an implicit cross-layer enum the API never validates (web/static/app.js:440-446,630-632).
- The server binds non-loopback addresses if asked (operators may add their own auth) but emits a loud one-time warning; the browser guard is CSRF-only, the network guard is bind-address-only (internal/httpapi/server.go:295-305).
- **[weird]** The healthz version string is process-global (package atomic), so two Server instances in one process always report the same version (internal/httpapi/server.go:1235-1253).
- **[weird]** Two different "never" timestamp conventions coexist in one API: PublisherKeywordEntry.last_published is RFC3339 UTC and OMITTED when zero, while companion timestamps serialize Go zero time and the UI string-compares against '0001-01-01T00:00:00Z' (internal/httpapi/server.go:756-758; web/static/app.js:992-994,1044).

### 5.12 Licensing and redistribution constraints

- MPL discipline is architectural, not just legal: MPL-2.0 is file-level copyleft, so ALL integration with anacrolix/torrent routes through extension APIs (piece callbacks, LocalLtepProtocolMap.AddUserProtocol, direct DHT library access) with zero patches — the stated motive includes retaining the option to ship a proprietary product. A rewrite that patches the engine directly breaks both the license posture and the design forcing-function (docs/05-integration-design.md:20,172; CLAUDE.md:76).
- **[weird]** CLAUDE.md/AGENTS.md speak of "the vendored library", but there is no vendor/ directory — anacrolix/torrent is a normal Go module dependency, and the full-source clones under research/torrent-clients/ are reference-only reading material, not build inputs; the "no patches" rule is enforced by not forking (go.mod:8; AGENTS.md:148).
- **[weird]** ledongthuc/pdf is BSD-3-Clause, NOT MIT — earlier docs mis-attributed it, and THIRD_PARTY_LICENSES self-declares as "the authoritative attribution", overriding all other documentation; regenerating attribution from stale docs would reintroduce the bug. Full license text is reproduced only for the BSD-3-Clause deps (the BSD binary-redistribution clause requires it) while MPL/Apache/stdlib entries are URL-only — the asymmetry is the point of the file (THIRD_PARTY_LICENSES:66-97,110-136; CHANGELOG.md:2041-2052).

Copyright identity is "The SwartzNet Authors", 2026, with no CLA/DCO machinery (contributions under Apache-2.0 §5 defaults) (docs/09-v1-blocker-research.md:250-254; LICENSE:130-136,178).

### 6.1 Contradictions and defects (things that misbehave today)

- **Bootstrap admission gate admits ANY unknown pubkey, inverting its documented default-deny.** `bloomPolicy` is a self-described placeholder that never reads the Bloom filter (only nil-checks it) and returns `tracker.Threshold(cand, 0.3)`; unknown pubkeys score `defaultUnknownScore = 0.5`, so every valid-sig crawled or sync-observed publisher is admitted into the Layer-D lookup set (up to `MaxTrackedPublishers = 100`) with zero vetting. Same defect in `countStrongEndorsers`: unknown endorsers pass the `>= 0.5` bar (0.5 >= 0.5), so 3 freshly-generated Sybil pubkeys clear the endorsement threshold for free. Production defaults always wire bloom+tracker, so the permissive path is the live path; the comment's referenced "test-only BloomOverride helper" does not exist anywhere in the repo (internal/daemon/bootstrap.go:443-484; internal/reputation/reputation.go:75,224-232,313-318; internal/config/config.go:242-244). Verifier: a test pins the permissive behavior, but the comment's described "2-Bloom-hits OR 1-anchor-overlap" rule is implemented nowhere.
- **Capability downgrades are never reflected on the wire.** The only outgoing `peer_announce` unconditionally ORs `DefaultServices()` (0x2ED, including BitShareLocal/FileHits/ContentHits) into the announced mask, so a node set to ShareLocal=0 — which rejects every inbound query — keeps advertising itself as query-capable; remote peers query a node that always rejects. Only the Publisher bit reflects live state. This contradicts both the BEP draft and `SetCapabilities`' "takes effect on the next handshake" doc (internal/swarmsearch/protocol.go:551-556; internal/swarmsearch/handler.go:688).
- **"Save sharing settings" (web UI and native GUI) silently clobbers the Publisher capability bit.** Both frontends POST only `{share_local, file_hits, content_hits}`; `req.Publisher` decodes to 0 and the handler wholesale-replaces the Capabilities struct, reverting the Publisher=1 set at engine startup and thereby disabling Layer-D pubkey gossip (`pk` on peer_announce + BitLayerDPublisher) until daemon restart (internal/httpapi/web/static/app.js:894-898; internal/httpapi/server.go:1217-1222; internal/gui/settings.go:313-318; internal/swarmsearch/protocol.go:550-563).
- **The L1 "in-swarm only" sharing level shares nothing.** GUI, web UI, and docs all offer L1 as a working level ("Peers can ask you about torrents you and they share"), but the handler fails closed and rejects every query at ShareLocal==1 with RejectShuttingDown because no swarm-aware searcher exists — a deliberate security fix disclosed only in a code comment and the CHANGELOG. Users selecting L1 believing they share in-swarm results share nothing (internal/swarmsearch/handler.go:680-691; internal/gui/settings.go:35; internal/httpapi/web/index.html:163-165; docs/06-bep-sn_search-draft.md:117).
- **Companion subscriber ingests without attribution or publisher verification.** `Subscriber.ingest` writes TorrentDoc/ContentDoc with no publisher attribution (`TorrentDoc.SignedBy` exists for exactly this and is never set), and `CompanionIndex.Publisher` is never cross-checked against the followed pubkey. Additionally, the documented `GeneratedAt` snapshot dedup is implemented nowhere — every sync unconditionally re-ingests all records (internal/companion/subscriber.go:97-100,169-214,249-308,492-498). Verifier: doc.go:28-31 advertises an `import.go` (M11d) namespacing layer that does not exist.
- **Download-slot accounting has two defects.** (a) Queue promotion on completion is skipped entirely when no Bloom filter is loaded: `autoConfirmOnComplete` returns on `bf == nil` before reaching `promoteQueuedLocked`, the only completion-triggered promotion site — with BloomPath unset or a bloom load failure, a completed torrent never frees its slot until pause/remove/cap-change (internal/engine/engine.go:1969-1985 vs queue.go:29-31; mitigated by defaults setting BloomPath). (b) `countActiveDownloads` never inspects file priorities despite the documented "any non-None file priority" rule, so an incomplete torrent whose files were all manually set to "none" still has BytesMissing > 0 and permanently occupies a slot (internal/engine/queue.go:25-31,64-90; internal/engine/files.go:113-136).
- **ZIM extraction never works via the live pipeline.** `ZimExtractor` requires `io.ReaderAt`, but the anacrolix `torrent.Reader` deliberately exposes only Read/Seek and the engine passes it straight through with no adapter — every daemon-fed `.zim` errors and is silently counted as skipped at Debug level; only tests (bytes.Reader/os.File) ever exercise the extractor. The comment "the engine's anacrolix file reader satisfies this" is factually wrong (internal/indexer/extractors/zim.go:68-75; internal/engine/engine.go:2028; internal/indexer/pipeline.go:190-192).
- **Layer-D lookup queries the FIRST token, not the "most distinctive (longest non-stopword)" the spec and code comment both claim.** `Tokenize` preserves appearance order with no length ranking and `Query` takes `tokens[0]` — searching "new ubuntu" queries the DHT for "new" (internal/dhtindex/lookup.go:257-279; internal/dhtindex/tokenize.go:84-124; docs/07-bep-dht-keyword-index-draft.md:245).
- **Torrent hits carry a garbage freshness timestamp on the wire.** The only production LocalSearcher never populates `LocalHit.AddedAt/Seeders/Leechers`; `hitsToWire` unconditionally serialises `T: h.AddedAt.Unix()`, so every torrent hit sends t = -62135596800 (zero time, year 1). S/L are omitted via omitempty rather than sent as 0 (internal/engine/swarmadapter.go:81-89; internal/swarmsearch/handler.go:801-808).
- **Reputation feedback is inconsistent across surfaces.** Downloads never auto-boost indexer reputations: `RecordConfirmed`'s comment promises M5d wiring to the download-succeeded event, but `autoConfirmOnComplete` only does `bloom.Add` (internal/reputation/reputation.go:177-192; internal/engine/engine.go:1949-1986). HTTP `POST /confirm` (used by CLI and web UI) also only does `bloom.Add`, while the native GUI additionally calls `RecordConfirmed` — so `hits_confirmed` in /status only ever moves via the GUI (internal/httpapi/server.go:818-837 vs internal/gui/search.go:411-433). The web UI flag button shows an unconditional "flagged" success even when the hit has no source attribution and the server demoted nobody; the native GUI correctly reports "no reputations changed" in that case (internal/httpapi/web/static/app.js:363-371; internal/httpapi/server.go:866-874).
- **Trusted publishers are demoted by flags despite the documented exemption.** trust.go promises flags against trusted publishers are "logged but NOT automatically demoted", but no flag path (HTTP or GUI) checks the trust store — attributed trusted publishers get `RecordFlagged` like anyone else (internal/trust/trust.go:12-14; internal/httpapi/server.go:874; internal/gui/search.go:460).
- **`/search` is strictly sequential across the three layers despite the "in parallel where possible" comment** — worst-case latency is local + ~2.5 s swarm + ~5.5 s DHT summed (internal/httpapi/server.go:495-609).
- **`POST /config/rate-limit` cannot do a partial update.** The handler unconditionally sets both limits; an omitted field decodes to 0 and clears that cap to unlimited, so changing only upload requires round-tripping the current download value. The doc comment contradicts itself (zero = "do not change" and zero = "unlimited") (internal/httpapi/server.go:1096-1132).
- **`GET /aggregate` reports the static `DefaultServices()` constant (0x2ED) instead of the live announced bits** — a publishing node announces 0x2FD but /aggregate reports 0x2ED. Because the announce ORs DefaultServices in, the endpoint can only omit live bits (publisher/share-swarm), never claim extra ones (internal/httpapi/aggregate.go:130-133 vs internal/swarmsearch/protocol.go:551-555).
- **`--regtest`/`--dht-insecure` require two differently-named env gates in sequence, none documented anywhere.** cmd_add refuses without `SWARTZNET_UNSAFE=1`; after setting it, `config.Validate` fails again demanding `SWARTZNET_ALLOW_REGTEST=1`. `SWARTZNET_LOG` is likewise undocumented. Verified empirically; the project's own testbed compose runs these flags with neither var set and would fail (cmd/swartznet/cmd_add.go:65-73; internal/config/config.go:291-300; testbed/docker-compose.dht.yml:61).
- **`dht-smoke` exits PASS/0 even when every stress put fails** — run() swallows runStress's only error with a Warn log, contradicting its own doc ("does not fail the exit status unless ALL puts fail"). Its bootstrap wait loop also degenerates into a busy spin once `bootstrapCtx` expires because `srv.Bootstrap()` blocks unbounded by that context while the empty `Done()` case fires every iteration (cmd/dht-smoke/main.go:22-25,72-92,172-179,300-302).

- **GUI About dialog reports the wrong license**: "MPL 2.0 (engine) + MIT (SwartzNet code)", but LICENSE, README, and THIRD_PARTY_LICENSES all say Apache 2.0 — user-visible misinformation in the shipped binary (internal/gui/app.go:311).

### 6.3 Doc drift (docs claim X, code does Y — or behavior exists undocumented)
